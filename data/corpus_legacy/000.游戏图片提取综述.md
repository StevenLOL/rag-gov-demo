## 1. 引言：为什么要做这件事

游戏图片资源提取的需求大致来自四个方向：

- **游戏考古 / 美术研究**：研究像素画技法、调色板设计、特定时期的美术风格（如 PC-98 的 16 色抖动、SFC 的 CGA 仿色）
- **Mod 制作**：替换原版素材，定制玩法
- **重制/移植**：把老游戏搬到现代平台（开源重制项目如 SuperSakura、EasyRPG）
- **资料整理 / 设定集**：把散落在资源文件中的 CG 收集成册

**但有一个铁律必须先说清楚**：游戏资源受版权保护。提取行为本身的技术讨论在中立学术语境下是合法的（美国《数字千年版权法》第 1201 条对"互操作性"有豁免，欧洲 InfoSoc 指令亦有类似条款），但提取出的素材**用途受原版权利约束**。个人学习、研究、评论一般属合理使用；商业使用、公开传播、制作"设定集"售卖等均需版权方授权。本文默认读者使用场景为个人学习与研究。

游戏图片资源的提取，本质上是三个层次的还原：

1. **数据层（文件容器）**：图片存在哪个文件里？是单文件还是打包在档案里？
2. **像素层（色彩编码）**：像素数据怎么组织？用什么压缩？调色板在哪？
3. **语义层（图元归属）**：散落的精灵怎么拼成完整画面？瓦片怎么组合成地图？

只有把这三层全部还原，才能得到一张可用的原图。

## 2. 理论基础：像素数据的四种基本形态

要理解游戏图片格式，必须先理解"一张图在磁盘上到底长什么样"。根据像素数据在文件中的组织方式，所有格式可以归为**四大基本形态**，这四形态的排列组合构成了游戏格式百花齐放的表象。

![图5：像素数据的四种基本形态](images/026/fig5_four_morphologies.png)

### 2.1 形态一：调色板索引（Indexed Color）

**这是游戏资源最经典、也最容易让新手踩坑的形态。**文件里存的不是颜色值，而是调色板中的**索引号**。

```
调色板：  palette[0] = (255, 0, 0)    // 红
         palette[1] = (0, 255, 0)    // 绿
         palette[2] = (0, 0, 255)    // 蓝
         ...
像素数据：  0 0 1 1 2 2 1 1 0 0 ...
           ↓ ↓ ↓ ↓ ↓
真实颜色： 红 红 绿 绿 蓝 蓝 绿 绿 红 红 ...
```

每个索引的位数决定调色板大小：

| 位数（bpp） | 调色板容量 | 典型用途 |
|---|---|---|
| 1 bpp | 2 色 | 单色位图、掩码 |
| 2 bpp | 4 色 | GB/SMS 精灵 |
| 4 bpp | 16 色 | PC-98、SFC、MD 主流模式 |
| 8 bpp | 256 色 | VGA、PS1 大部分 2D 素材 |

**核心坑**：调色板经常**不与像素数据存放在同一个文件里**。一个 Galgame 可能用几十张 `.pic` 文件共享一个 `pal.dat`；一个 SFC 游戏的调色板可能嵌在关卡数据里。识别"调色板在哪"是独立于"像素怎么解码"的一个子问题。

![图3：调色板索引色工作原理](images/026/fig3_indexed_color.png)

### 2.2 形态二：RGB 直读（True Color / Packed Pixel）

每个像素直接存 RGB 三分量。常见子类：

- **15/16 bpp（Hi-color）**：RGB555 或 RGB565，每分量 5~6 位。PS1 / N64 / Dreamcast 常用
- **24 bpp（True Color）**：RGB888，现代主流
- **32 bpp（True Color + Alpha）**：RGBA8888，带透明通道

### 2.3 形态三：平面图（Planar）

**这是老派游戏机最容易卡住新手的地方。**像素数据不是按"一行像素连续存"的，而是**按位平面拆开**。

以 4bpp 平面模式为例，8 个像素占 4 个字节，但存法不是"像素 0、1、2、3、4..."，而是：

```
内存中的 4 个字节（4bpp 平面图，8 像素）：
  Byte 0: [b0_0 b0_1 b0_2 b0_3 b0_4 b0_5 b0_6 b0_7]   ← 平面 0
  Byte 1: [b1_0 b1_1 b1_2 b1_3 b1_4 b1_5 b1_6 b1_7]   ← 平面 1
  Byte 2: [b2_0 b2_1 b2_2 b2_3 b2_4 b2_5 b2_6 b2_7]   ← 平面 2
  Byte 3: [b3_0 b3_1 b3_2 b3_3 b3_4 b3_5 b3_6 b3_7]   ← 平面 3
第 i 个像素的调色板索引 = (b3_i << 3) | (b2_i << 2) | (b1_i << 1) | b0_i
```

PC-98 的 640×400 16 色显存就是三平面结构（B/G/R 三个 4bpp 平面），文件 dump 出来就是三个连续的大块，**必须按平面反交织**才能得到正确的像素。

**位平面的三种常见布局**：

1. **平面连续（Contiguous）**：平面0全部数据 → 平面1 → 平面2 → 平面3
2. **按行交错（Row-interleaved）**：每行包含4个平面的数据，如FGP格式每行16字节=4平面×4字节
3. **8像素块（Block-8）**：每4字节控制8个像素的4个平面，PC98 GPC格式使用

![图1：打包像素 vs 位平面存储](images/026/fig1_planar_vs_packed.png)

> **实战经验**：位平面布局错误是"竖条纹"症状的最常见原因。我们在SANGUO三国英雄、ETIN倚天屠龙记等多个游戏中都遇到了这个问题。

### 2.4 形态四：瓦片化（Tiled / Chunky Tile）

**NES / SFC / MD / PCE / GBA 的精灵和背景通常不是按扫描线存的，而是按 8×8 的"瓦片"存**。一个 16×16 的角色精灵被拆成 4 个 8×8 小块，每块独立存，且**块的排列顺序因平台而异**。

```
一个 16×16 SFC 精灵的典型 VRAM 布局：
  ┌──────┬──────┐
  │ 块 0 │ 块 1 │   ← 第一个 8×8
  ├──────┼──────┤
  │ 块 2 │ 块 3 │   ← 第二个 8×8
  └──────┴──────┘
在 VRAM 中的存储顺序可能是： 0, 1, 2, 3（线性）
也可能是：                  0, 2, 1, 3（NES 惯例的 2×2 交织）
```

如果不按平台约定的顺序重组，解码出来就是"乱码块拼图"。

### 2.5 四种形态的判断

```
拿到一段原始像素数据后，先问三个问题：
Q1: 数据量 ≈ 宽 × 高 × 1/2 ?    → 4bpp
Q2: 数据量 ≈ 宽 × 高 ?          → 8bpp
Q3: 数据量 ≈ 宽 × 高 × 2 ?      → 15/16bpp
Q4: 数据量 ≈ 宽 × 高 × 4 ?      → 32bpp RGBA
Q5: 数据量 ≈ 宽 × 高 × 4/8 倍?  → planar（如 4 平面）
Q6: 数据量远小于上述任一数值？  → 有压缩
```

## 3. 压缩算法：三大门派

90 年代游戏受磁盘空间限制，几乎每家公司都发明自己的压缩算法。但万变不离其宗，绝大多数可以归入三类。识别"用的哪类压缩"通常只需看压缩后数据的前几十个字节的行为。

### 3.1 门派一：游程编码（RLE）

**思想**：连续相同值用一个计数 + 一个值替代。

```
原始像素流：   A A A A A B B C C C C C C C C
RLE 编码后：  [5 A] [2 B] [8 C]
```

**变体极多**，主要区别在"计数与数据"怎么编码：

| 变体 | 编码方式 | 典型用户 |
|---|---|---|
| PCX 式 | 高 2 位为计数标志（11xxxxxx = 计数） | PCX、TGA 压缩模式 |
| 计数前置 | 先读 1 字节计数 N，再读 1 字节值 | 大量 2D 游戏 |
| 符号判别 | N < 0x80 表示字面 N+1 字节；N ≥ 0x80 表示下一个值重复 N-0x7F 次 | Apple PackBits、IFF ILBM |
| 分离表 | 计数流和数据流分离 | 部分 SNES/MD 游戏 |

我们在实战中验证了 5 种 RLE 变体：

1. **格式A（ETIN）**：命令字节 `0xFF` 后跟 `[count, value]`，`0xFF` 只在命令位置出现
2. **格式B（ETIN）**：高位标志法，`(count<<1)|flag`，flag=1时后跟value
3. **格式C（SANGUO）**：行内RLE，每行独立，`0xFF`为行结束标记
4. **PackBits（Apple）**：有符号字节，正=字面量，负=重复
5. **PCX式**：高2位`11`表示计数包

![图4：RLE游程编码原理](images/026/fig4_rle.png)

### 3.2 门派二：LZ 字典压缩（LZSS / LZ77）

**思想**：如果前面已经出现过这段数据，就存"向前偏移 + 长度"的引用。

```
原始： "ABCDABCDEF"
      ↑     ↑
LZSS：  ABCD [offset=4, len=6]      ← 第二个 ABCDEF 被替换为引用
```

LZSS 与 LZ77 的区别：LZSS 只在"引用"比"字面量"短时才使用引用，每个引用通常带 1 bit 标志位（0=字面量字节，1=偏移+长度对）。

```c
// 典型 LZSS 解压循环（伪代码）
while (输出未满) {
    flags = read_byte();              // 8 位标志
    for (bit = 0; bit < 8; bit++) {
        if (flags & (1 << bit)) {
            // 引用
            offset = read_byte() | ((read_byte() & 0xF0) << 4);
            length = (read_byte() & 0x0F) + 3;
            for (i = 0; i < length; i++)
                output[dst++] = output[dst - offset - 1];
        } else {
            // 字面量
            output[dst++] = read_byte();
        }
    }
}
```

**关键参数**（识别 LZSS 变体时要测）：窗口大小、偏移位数、长度位数、最小匹配长度、窗口初始填充（通常是 0 或 0x20）。

SNES 上的经典 LZSS 变体是 Nintendo 的"Type 1"压缩（第一字节 = `0x10` + 3 字节解压后长度），GBA 上是 BIOS LZ77 调用（第一字节 = `0x10`）。

**我们的 LZSS 解码器支持自动参数搜索**：遍历窗口大小(512/1024/2048/4096)、偏移位数(8-16)、长度位数(4-8)、最小匹配(2-4)的组合，找到能正确解压的参数。

### 3.3 门派三：熵编码 + 变换（高级）

**思想**：对出现频率不同的符号用不同长度的编码，压缩率更高但复杂度更高。

- **Huffman**：出现频率高的符号用短码
- **MTF + 算术编码**：把"最近用过的符号"编码得更短
- **MTF + 变长 delta 码**：PC-98 Pi 格式就是这一路的杰作

PC-98 的 Pi 格式使用了一个巧妙的"per-symbol MTF delta table"：对每个颜色 a 维护一个"最近跟随 a 的颜色栈"，然后用变长位编码（1x / 00x / 010xx / 011xxx...）表示"取栈顶第几位"——这样，频繁重复的图案会自动把栈顶配置成短码。

```
Pi 格式的 delta table 初始化（N = 调色板大小）：
  table[a][b] = (N + a - b) mod N
4bpp 图的变长码表：
  1x      → delta 0-1    (1/2 概率，2 bits)
  00x     → delta 2-3    (1/4 概率，3 bits)
  010xx   → delta 4-7    (1/8 概率，5 bits)
  011xxx  → delta 8-15   (1/16 概率，6 bits)
```

### 3.4 三大门派的识别口诀

```
看压缩数据的第一段字节行为：
  字节流有明显的"交替的 flag 字节 + 数据字节"模式  → RLE 或 LZSS
  flag 字节里高位 bit 全是 0/1 交替                 → LZSS（8 标志/字节）
  flag 字节里低 2 位是 11 时才连续                 → PCX 式 RLE
  数据开头就是"长度字段 + 紧跟压缩数据"            → 头部化压缩（如 GBA BIOS）
  数据混乱无规律、但有周期性重复片段               → Huffman / 算术编码
  数据就是"半宽的宽 × 半高的高"大小                 → 未压缩 4bpp
```

## 4. 核心问题拆解：五个必须解决的挑战

实际提取时，真正消耗时间的不是"解码算法"，而是下面五个前置问题。**按顺序解决，效率最高。**

### 挑战 1：这张图到底存在哪里？

游戏不会把一张图存成一个"标准的 PNG"。典型情况：

```
最简单：    title01.pic        一张图 = 一个文件
容器式：    graph.dat          多张图打包在一个档案里，需要偏移表
拼接式：    000.pak ~ 999.pak  一张 CG 拆成 N 个文件（如分块 CG）
附属式：    tile + map         瓦片 + 地图索引，需要组合才能看到整图
隐藏式：    exe 附加数据       图片嵌在可执行文件尾（BSS 段后）
```

**应对策略**：

| 现象 | 判断 | 处理 |
|---|---|---|
| 文件头是已知魔数 | 通用格式 | 直接用工具打开 |
| 文件名有规律（如 `bg*.dat`） | 自定义格式 | 用十六进制工具看头 32 字节 |
| 文件大小全是同一个数 | 未压缩定尺寸 | `sqrt(大小/2)` 大概就是宽 |
| 文件大小不等但都很大 | 容器式档案 | 找偏移表 |
| 找不到可疑文件 | 数据嵌在 exe | dump exe 到文件系统后段 |

### 挑战 2：调色板在哪里？

这是 indexed color 提取最头疼的一步。常见位置：

1. **像素文件头**（最理想）：头部 32~768 字节是调色板
2. **独立的调色板文件**：如 `pal.dat`、`system.pal`，可能多个像素文件共享
3. **调色板选择表**：多个调色板存在一个文件里，像素头部只存"用第几个调色板"（如 PC-98 SGV 的 `pal.dat` 多选一索引）
4. **嵌在关卡/脚本数据里**：每个场景加载时才把调色板写入显存，需要逆向脚本或模拟器 hook
5. **固定调色板**：硬件厂商固定（如 NES 整体 64 色固定），无需提取

**模拟器对照法**（最暴力但最有效）：在模拟器中跑游戏，用调色板查看工具 dump 当前显存调色板，就是真实使用的调色板。

**调色板定位技巧**：
- 在文件中寻找连续的、值在0-63范围内的字节块
- 渲染为16×1或16×16的色带，观察是否有合理的颜色过渡（肤色、天空蓝、草地绿）
- 注意调色板可能在文件头部、尾部、或独立的.PAL/.RGB文件中

### 挑战 3：压缩怎么解？

参见第3章。关键是先识别压缩类型，再选择对应的解码器。我们的工具集提供了：
- 5种RLE变体解码器
- 参数化LZSS解码器（支持自动参数搜索）
- 标准LZW + MGP2变体解码器

### 挑战 4：图像布局对不对？

这是"解码成功但图像不对"的最常见原因。需要验证：
- **位平面顺序**：平面0/1/2/3的排列是否正确
- **行宽（stride）**：是否有padding？实际渲染宽度是否等于文件中的宽度字段？
- **扫描线方向**：从上往下还是从下往上？
- **瓦片顺序**：8×8小块的排列顺序是否符合平台约定？

> **核心教训（SANGUO GRP）**：文件中的`w2`字段是RLE编码的行宽，不等于实际渲染宽度`w`。用`w2`渲染会产生右侧竖条纹。必须用`w`作为实际宽度。

### 挑战 5：透明色怎么处理？

- **索引色透明**：指定某个调色板索引为透明（通常是0，但不一定！）
- **黑色背景透明**：很多DOS游戏用纯黑(0,0,0)作为透明色，但角色身上的黑色部分也会被误判为透明
- **解决方案**：使用"边界检测法"——只将与图像边界连通的黑色区域设为透明，角色内部的黑色保留

## 5. 五阶段提取法：从二进制到可视图像

基于 12 个游戏的逆向实践和社区 20+ 年沉淀，我们总结出一套可复现的五阶段迭代法。

![图2：游戏图片提取五步法](images/026/fig2_five_steps.png)

### 阶段 1：侦察（Reconnaissance）

**目标**：把所有可能是图片的文件找出来，并建立"原图对照表"。

**具体动作**：
```bash
# 1. 按大小分布排序——同一尺寸的文件很可能同属一类
find ./game_dir -type f -exec ls -la {} \; | awk '{print $5}' | sort -n | uniq -c
# 2. 用 file 命令识别魔数
file ./game_dir/*
# 3. 找所有扩展名分布
find ./game_dir -type f | sed 's/.*\.//' | sort | uniq -c | sort -rn
# 4. 用模拟器截图，记录"游戏里看到什么 → 对应哪个文件"的映射
```

**关键工具**：模拟器（Neko Project II / PCSX / mGBA / Mesen）+ 显存查看器 + 调色板查看器。

### 阶段 2：假设（Hypothesis）

**目标**：对每个文件形成"这是什么格式"的初步假设，写成结构化笔记。

**十六进制头部判读清单**（按顺序看）：
```
[0x00]  前 4 字节    → 是魔数吗？对照 Just Solve / XentaxWiki 数据库
[0x04]  4~16 字节   → 有没有看起来像宽/高的 16/32 位值？
[0x10]  剩余头部    → 是不是调色板？大小是否符合 16×3 或 256×3？
[0xNN]  主体数据    → 有压缩规律吗？熵值多少？
```

**魔数识别捷径**：Kaitai Struct 官方画廊、Just Solve the File Format Problem、XentaxWiki 都收录了上千种游戏格式的头部结构。

### 阶段 3：解码（Decode）

**目标**：写出第一个解码脚本，跑出第一张 PNG。

**推荐使用 Kaitai Struct 作为第一步**——它让你用声明式 YAML 描述格式，自动生成 Python/C++/Java 解析器，避免一开始就陷入手写解析器的边角 bug。

```yaml
# 一个假设的格式描述
meta:
  id: my_game_image
  file-extension: pic
  endian: le
seq:
  - id: magic
    contents: 'IMG'
  - id: width
    type: u2
  - id: height
    type: u2
  - id: palette
    type: palette_entry
    repeat: 16
  - id: pixel_data
    size: width * height / 2
types:
  palette_entry:
    seq:
      - id: r
        type: u1
      - id: g
        type: u1
      - id: b
        type: u1
```

```python
# 配合 Kaitai 生成的 Python 代码做像素还原
from kaitaistruct.my_game_image import MyGameImage
from PIL import Image
img = MyGameImage.from_file("title01.pic")
png = Image.new("RGB", (img.width, img.height))
for y in range(img.height):
    for x in range(img.width):
        byte_idx = (y * img.width + x) // 2
        nibble = img.pixel_data[byte_idx]
        idx = (nibble >> 4) if x % 2 == 0 else (nibble & 0x0F)
        pal = img.palette[idx]
        png.putpixel((x, y), (pal.r, pal.g, pal.b))
png.save("title01.png")
```

**目标**：从"解码一张"变成"解码全部"。

### 一个值得遵守的纪律：先写纯语言描述，再写新实现

SuperSakura 作者 Bunnylin 逆向 PC-98 图形格式时的经验：**直接移植原转换器代码有版权风险**。正确做法是用调试器读懂算法逻辑，用自然语言记录，然后重新实现。

## 7. 实战案例：五个经典格式的完整破解

### 7.1 案例一：PC-98 GPC 格式（YOHGAS妖精战士、K2华丽的人生2）

**识别特征**：文件前16字节为 `PC98)GPCFILE   \x00`

**头部结构**：
```
偏移  长度  内容
0x00  16    魔数 "PC98)GPCFILE   \0"
0x10  2     scans（扫描次数，1=正常，2=隔行扫描）
0x14  2     palette_offset（通常=48）
0x18  2     image_offset（通常=84）
```

**调色板**（偏移palette_offset开始）：
```
+0:  colorcount（LE16，通常=16）
+2:  transcolor（LE16，透明色索引，通常=2）
+4:  16个颜色，每个2字节
     格式: (G<<8) | (R<<4) | B，各4位，需<<4转8位
     解析: g=((pd>>8)&0xF)<<4, r=((pd>>4)&0xF)<<4, b=(pd&0xF)<<4
```

**图像区**（偏移image_offset开始）：
- 8像素块位平面布局：每4字节控制8个像素的4个平面
- 字节0=平面0，字节1=平面1，字节2=平面2，字节3=平面3
- 像素索引 = (plane3_bit<<3)|(plane2_bit<<2)|(plane1_bit<<1)|plane0_bit

**破解关键**：调色板是GRB顺序（非RGB），位平面是8像素块布局（非按行交错）。

### 7.2 案例二：SANGUO GRP 格式（三国英雄）

**识别特征**：`.grp` 文件，头部含宽度字段

**核心陷阱——行宽不等于渲染宽度**：
```
文件头部有两个宽度字段：
  w  = 实际渲染宽度
  w2 = RLE编码的行宽（用于压缩）

错误做法：用 w2 作为图像宽度 → 右侧出现竖条纹
正确做法：用 w 作为图像宽度，RLE解码时按 w2 行宽解码
```

**RLE编码**：行内RLE，每行独立，`0xFF`为行结束标记。

**破解关键**：这是我们花了最长时间才解决的问题。最初假设`w2`是渲染宽度，导致所有图片右侧有竖条纹。直到对比游戏截图才发现实际宽度应该是`w`。

### 7.3 案例三：HR 高报酬战将（PC-98移植）

**识别特征**：`.grp` 文件，PC-98平台移植

**核心陷阱——8bpp不是256色**：
```
表面看是8bpp（每像素1字节），但不是256色调色板索引
实际是"高4位颜色索引 + 低4位亮度"的复合格式：
  color_idx = byte >> 4    (0-15，16色调色板)
  brightness = byte & 0x0F (0-15，亮度级别)
  最终颜色 = palette[color_idx] * (brightness / 15)
```

**4bpp精灵也不是颜色索引**：
```
4bpp不是16色调色板索引，而是16级亮度遮罩
配合4种玩家颜色（红/蓝/绿/黄）进行着色：
  最终颜色 = player_color * (brightness / 15)
```

**破解关键**：不能被"8bpp=256色"的常识误导。PC-98游戏常用复合格式来在有限色深下实现更多视觉层次。

### 7.4 案例四：JPM MGP2 格式（金瓶梅）

**识别特征**：`.MGP` 文件，LZW压缩

**核心陷阱——非标准LZW变体**：
```
标准LZW：清除码后，next_code重置为初始值
MGP2变体：清除码后，第一个代码也会增加next_code

这导致标准LZW解码器在ITEM.PAT上失败
必须修改：处理清除码后，读取第一个代码时也要执行next_code++
```

**破解关键**：LZW的变体差异往往只在一两个细节上。当标准LZW失败时，检查清除码处理、代码位宽变化、初始字典大小等细节。

### 7.5 案例五：PC-98 MAG 格式（通用绘图格式）

MAG 格式是 PC-98 时代事实标准的图片格式，由流行的绘图软件 Multi Paint System 的作者创造，结构复杂但资料齐全。

![图6：PC-98 MAG格式三流压缩结构](images/026/fig6_mag_structure.png)

**侦察**：拿到一个 `.mag` 文件，用十六进制工具看头 32 字节：
```
00: 4D 41 4B 49 30 32 20 20   "MAKI02  "          ← 魔数
08: 01 00 ...                模型字节：01 = PC-98 4bit
0C: 05 C0 ...                作者名（Shift-JIS）
14: 06 90 ...                评论（Shift-JIS）
20: ...                      色彩起始屏幕行
24: ...                      宽度-1、高度-1
28: ...                      flag A 段偏移
2C: ...                      flag B 段偏移
30: ...                      像素数据段偏移
34: ...                      调色板（16×3 字节，注意是 GRB 顺序！）
```

**关键陷阱一：调色板是 GRB 顺序**

调色板字节顺序是 Green-Red-Blue，不是 RGB。如果不交换，解码出的图会偏色（绿色通道和红色互换）。

另外，**调色板字节的高 4 位有效**：MAG 用的是 12bit 调色板（每分量 4bit），存储时用 8bit 字节，但**只有高 4 位有效**。正确还原：
```python
color = ((byte & 0xF0) >> 4) * 17  # 4bit → 8bit
```

**关键陷阱二：三流压缩结构**

MAG 的像素数据分为**三个独立位流**，需要并行读：
- **Flag A 位流**（bit级）：每16个像素一个bit。0=后面16像素直接从像素流读；1=用flag B的操作码从已解压数据复制
- **Flag B nibble流**（4bit级）：15个操作码，是针对抖动图案优化的相对位置
- **像素索引数据流**（nibble级）：实际的调色板索引

Flag B 的 15 个操作码是 MAG 设计的精髓——它们是**针对抖动图案优化的相对位置**，比如"上 4 行右 1 像素"正好对应经典的棋盘抖动周期。

**关键陷阱三：垂直 XOR 滤波**

MAG 的像素数据经过一层**垂直 XOR 滤波**：从第 3 行起，每个字节与上方第 2 行的对应字节异或，目的是消除大面积重复。解码后要再做一次"解异或"：
```python
for y in range(2, height):
    for x in range(width_bytes):
        data[y][x] ^= data[y-2][x]
```

**验证**：解码结果与模拟器截图对照。如果偏色 → 调色板顺序错；如果"鬼影" → XOR 滤波顺序错；如果碎片化 → flag 流没同步。

现成参考实现：**mag2png**（开源 C）、**sakutool**（SuperSakura 项目）、**Recoil**。

## 8. 进阶话题：纹理图集与精灵重组

### 8.1 什么是纹理图集

现代 GPU 不喜欢频繁切换纹理绑定，所以引擎会把所有小图打成一张大图：

![图7：纹理图集与精灵重组](images/026/fig7_texture_atlas.png)

```
atlas.png (1024×1024) + atlas.json
atlas.json：
  {
    "hero1": { "x": 0,   "y": 0, "w": 64, "h": 128 },
    "sword": { "x": 200, "y": 80, "w": 32, "h": 32 },
    ...
  }
```

### 8.2 提取时的关键问题

- **Premultiplied Alpha**：Unity 常用，如果直接转 PNG 会发现颜色"褪色"。需要先 un-premultiply
- **PVRTC/ASTC/ETC 压缩**：移动端格式，需要专用解码器（PVRTexTool、UnityPy 内置）
- **Trimmed Sprite**：打包时被裁掉了透明边缘，需要从 atlas 数据中还原原始尺寸和偏移
- **Sprite Rotation**：MaxRects 算法可能旋转精灵，需要从 metadata 读 rotation 字段

### 8.3 推荐工具

| 工具 | 平台 | 特点 |
|---|---|---|
| **UnityPy** | Python | 脚本化最强，能直接读 Sprite 类并导出 PNG |
| **AssetStudio** | Windows GUI | 可视化浏览，适合一次性提取 |
| **AssetRipper** | 跨平台 C# | 导出为完整 Unity 项目，可用于"反向工程到再工程" |

## 9. 常见陷阱与调试技巧

### 9.1 十二种典型症状排查表

| 症状 | 可能原因 | 排查方向 |
|---|---|---|
| 全黑/全白 | 调色板全错或bpp判断错 | 检查调色板偏移、bpp |
| 颜色错乱（红变蓝） | 调色板顺序BGR/RGB反了 | 交换R/B通道 |
| 颜色偏暗/偏亮 | 调色板位深不对（6bit vs 8bit） | 6bit值×4或左移2 |
| 竖条纹 | 位平面顺序错或行宽错 | 检查平面排列、w vs w2 |
| 横条纹 | 扫描线方向反或隔行扫描 | 翻转图像或去隔行 |
| 图像倾斜/剪切 | 行对齐stride/padding错 | 检查每行字节数 |
| 上下颠倒 | 扫描线方向反（BMP自下而上） | 垂直翻转 |
| 碎片化/乱码块 | 瓦片化布局未重组 | 按平台约定重组8×8块 |
| 鬼影/重影 | XOR滤波未还原或差分编码 | 检查是否有预测滤波 |
| 部分颜色错 | 调色板高位nybble有效性 | 12bit调色板需`| 0x0F`或×17 |
| 透明区域错误 | 透明色索引不是0 | 检查文件头的transcolor字段 |
| 角色内部黑色变透明 | 黑色背景透明误判 | 使用边界检测法保留内部黑色 |

### 9.2 常见陷阱详解

#### 陷阱 1：Endianness 搞错
- PC/PS1/GBA/MD 都是小端
- X68000、PC-88 一些格式、MAG 是大端
- PS2 是小端，但游戏内自定义格式可能大端
- **诊断**：宽高字段读出来像是 65535 倍或 1/256 倍，就是 endianness 反了。

#### 陷阱 2：行对齐（Stride / Padding）
图片每行不一定是"宽度 × 每像素字节数"，可能有 padding 到 4 字节或 8 字节边界。BMP 是经典例子：
```
实际存储宽度 = ceil(width × bpp / 32) × 4 字节
```
**诊断**：解码出的图有"斜剪切"，就是 stride 算错。

#### 陷阱 3：调色板类型混淆
- **BGR vs RGB**：Windows GDI 用 BGR
- **12bit vs 24bit**：PC-98 是 12bit（每分量 4bit），直接当 8bit 会偏色
- **5bit vs 6bit**：SFC 是 5bit per channel（32768 色），GBA 也是 5bit
- **YJK / YUV**：MAX / FM-Towns 用 YJK，需要转换到 RGB

#### 陷阱 4：扫描线方向
- Windows BMP 从下往上
- 大部分游戏从上往下
- 某些 nes/fc 游戏按"瓦片列"而不是"瓦片行"存

#### 陷阱 5：内存版 vs 文件版差异
游戏 VRAM 里的精灵图和文件 dump 出来的可能不一样——VRAM 里是"瓦片交织 + 附加属性字节"的结构，文件里是"压缩后的连续像素"。**不要假设文件格式 = 显存格式**。

#### 陷阱 6：加密 / 混淆
很多商业游戏会做一层简单的加密防提取：
- **固定 XOR**：整个文件 XOR 一个常数或密钥
- **字节交换**：高低 nibble 交换、字节序反转
- **文件头篡改**：故意写错魔数
- **识别**：熵分析——如果数据看起来"接近随机"但实际是图像，通常有 XOR；如果数据"熵正常但魔数不对"，可能只是魔数被改。

### 9.3 调试技巧：差分法

如果某张图解码完全不对：
1. **换一张结构相似但内容简单的图试**（比如纯色背景图），如果那张能解码 → 说明算法对，是特例问题
2. **只解码前几行**，看是否与原图对应
3. **输出中间值**：把 flag A 的位流打印出来，看是否像"每 16 像素一个 bit"的节奏
4. **用模拟器 hook 显存写入**，看真实像素流是什么样

### 9.4 我们的独创方法论：单色平面验证法

当位平面顺序不确定时，不要猜。用以下方法系统验证：

1. 单独渲染每个平面为灰度图（平面值0/1映射为黑/白）
2. 观察哪个平面对应图像的哪个位（高位/低位）
3. 尝试144种平面排列组合（4!×3!×2!），找到正确的
4. 用游戏截图作为ground truth验证

这个方法在ETIN、SANGUO、SWDA等多个游戏中被证明有效。

## 10. 法律与伦理边界

这是绕不开的一节。逆向前请确认以下红线：

### 10.1 合法的典型场景

- **个人学习研究**：拆开文件理解格式
- **互操作性**：让旧游戏在新平台运行（开源重制、模拟器）
- **学术发表**：在论文、技术博客中讨论格式（不附带原素材）
- **备份所有权副本**：自己拥有正版光盘/卡带
- **已经公有领域的作品**：如 1980 年代很多日本同人游戏、某些开源游戏

### 10.2 高风险的场景

- **商业使用**：把提取的 CG 做成设定集、壁纸包、周边售卖
- **公开传播**：在社交平台分享完整的原版 CG 集
- **克隆游戏**：用原版素材做"精神续作"
- **伪造官方**：用原版素材冒充官方重制版

### 10.3 灰色地带

- **Mod 制作**：大多数单机游戏 Mod 处于灰色地带，部分厂商（Bethesda、CDPR）明确允许；部分（任天堂）零容忍
- **AI 训练**：用提取的素材训练 AI 模型，法律界尚未定论，但风格模仿可能涉及人格权
- **直播/视频**：展示游戏画面属于合理使用，但"只展示提取的美术"有风险

### 10.4 实操建议

1. **先查版权状态**：用 TCRF（The Cutting Room Floor）、MobyGames 查版权方是否还活跃
2. **再查是否有官方渠道**：Steam 重制版、官方设定集——优先支持官方
3. **提取的素材永不外传**：只在本地研究
4. **逆向方法论可以分享，格式规格可以写文档，但原素材不发布**
5. **如果做开源重制，用自由许可的替代素材**（如 CC0 像素画）

## 结语：从"提取"到"理解"

游戏图片资源提取的技术价值，**不止于"拿到几张图"**。每一份逆向出来的格式规格，都是对当年工程师与美术师在硬件约束下创造性解法的尊重——PC-98 美术师在 16 色、4096 色调色板、640×400 的约束下，用有序抖动模拟出 256 色的视觉感受；MAG 格式的作者把"抖动图案的统计特征"编码成 15 个专门的相对位置操作码；Pi 格式的作者用 per-symbol MTF 把"最近用过的颜色"编码得几乎免费。

今天提取这些资源，既是为了保存这份工艺，也是为了理解**在资源极度受限时如何做设计**——这种思维在今天的嵌入式系统、带宽受限的流媒体、以及 Web3 的小体积资产设计中依然适用。

把每一次"成功解码一张图"都当作一次与 30 年前某个像素画师的对话。这也是这项工作最大的乐趣。

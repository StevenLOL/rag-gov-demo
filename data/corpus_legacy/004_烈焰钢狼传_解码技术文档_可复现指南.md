## 0. 方法论总览

面对一个未知格式的 DOS 游戏资源包，最优分析路径是**从外到内、从粗到细**的四层递进：

```
第一层: 归档层  →  识别容器格式，解包出独立文件
第二层: 分类层  →  按扩展名/魔数/文件头特征分类
第三层: 格式层  →  对每类文件推导二进制结构
第四层: 实现层  →  编写解码器，验证，批量转换
```

每一层的结论都成为下一层的输入。关键原则：**先观察，后假设；先验证单文件，后批量处理。**

## 1. 第一层：归档层 — DDT 格式推导与解包

### 1.1 观察

游戏目录中存在一个异常大的文件：

| 文件 | 大小 | 特征 |
|------|------|------|
| `MWOLF.DDT` | 22.80 MB | 远大于其他文件，单个文件占游戏资源 95%+ |

单个 22MB 文件在 DOS 时代几乎必然是**资源归档容器**。

### 1.2 头部分析

用十六进制编辑器打开，读取前 32 字节：

```
偏移:  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0000:  BA 05 00 00 54 49 54 4C 45 30 30 41 00 00 A4 55
0010:  00 00 54 49 54 4C 45 30 30 42 00 00 00 9C A5 55
```

**推导步骤：**

1. `BA 05 00 00` 按小端 uint32 解析 = **1370**。这是一个合理的"文件总数"量级。
2. 从偏移 0x04 开始，数据呈现明显的**16字节周期性**：
   - 前12字节是可打印 ASCII（`TITLE00A\0\0\0`），即文件名
   - 后4字节是小端 uint32（`A4 55 00 00` = 21924），即偏移量
3. 验证：`4 + 1370 × 16 = 21924`，正好等于第一个条目的偏移量。**数据区从 21924 开始。**

### 1.3 格式定义

![DDT格式结构](images/01_ddt_format_structure.png)

```
偏移量          大小            说明
0x0000          4 字节          uint32 LE: 文件总数 N
0x0004          N × 16 字节     目录项数组
  ├─ [0..11]   12 字节         文件名 (ASCII, null 填充至12)
  └─ [12..15]  4 字节          uint32 LE: 数据绝对偏移量
0x0004+N×16     可变            连续数据区 (无压缩, 原样存储)
```

**文件大小计算：** 目录项不存大小，`size[i] = offset[i+1] - offset[i]`，最后一个文件到归档末尾。

### 1.4 解包实现

```python
import struct
from pathlib import Path

def extract_ddt(ddt_path: str, output_dir: str):
    ddt_path = Path(ddt_path)
    output_dir = Path(output_dir)
    output_dir.mkdir(parents=True, exist_ok=True)

    with open(ddt_path, 'rb') as f:
        file_count = struct.unpack('<I', f.read(4))[0]

        # 读取目录项
        entries = []
        for _ in range(file_count):
            raw = f.read(16)
            name = raw[:12].rstrip(b'\x00').decode('ascii', errors='replace')
            offset = struct.unpack_from('<I', raw, 12)[0]
            entries.append((name, offset))

        # 验证数据区起始
        assert entries[0][1] == 4 + file_count * 16

        # 提取每个文件
        archive_size = ddt_path.stat().st_size
        for i, (name, start) in enumerate(entries):
            end = entries[i + 1][1] if i + 1 < file_count else archive_size
            size = end - start
            if size == 0:
                continue
            f.seek(start)
            (output_dir / (name or f'unnamed_{i:04d}')).write_bytes(f.read(size))

    print(f'提取完成: {file_count} 条目, 输出至 {output_dir}')
```

## 2. 第二层：分类层 — 确定分析优先级

解包后按**文件数量 × 信息密度**排序，优先分析数量最多、视觉价值最高的格式：

```
优先级 1: .CMP (1189个, 占87%, 全部图片)  ← 核心难点
优先级 2: .PAL (1个, 但所有图片都依赖它)   ← 必须先于CMP解码
优先级 3: .XMI (23个, 音乐)                 ← 标准格式变体
优先级 4: .DAT/.IMG (游戏目录中29个IMG)     ← 可能是无压缩图片
优先级 5: .UNI/.TIC/.TIN/.TRM/.TTY (156个) ← 非视觉数据, 保留原始即可
```

**策略：** 先搞定调色板（最简单），再攻克 CMP（最难、价值最高），其余顺势而为。

## 3. 第三层：格式层 — 逐类推导

### 3.1 PAL 调色板（5分钟搞定）

**观察：** `MAINCOL.PAL` 恰好 768 字节 = 256 × 3。这是标准的 VGA 256 色调色板大小。

**推导：**
- VGA DAC 寄存器是 6 位的（0-63），所以每通道值范围 0-63
- 转换到 8 位：`v8 = (v6 << 2) | (v6 >> 4)`（等效 `v6 × 255 / 63`）
- 颜色索引 0 通常是背景/透明色

**实现：**
```python
def load_palette(pal_path: str) -> list:
    data = Path(pal_path).read_bytes()
    return [((data[i*3]<<2)|(data[i*3]>>4),
             (data[i*3+1]<<2)|(data[i*3+1]>>4),
             (data[i*3+2]<<2)|(data[i*3+2]>>4)) for i in range(256)]
```

### 3.2 CMP 压缩图片（核心难点）

#### 3.2.1 文件头分析

取 `TITLE00A.CMP`（文件名暗示是标题图，最容易目视验证），读取前 4 字节：

```
80 02 E0 01
```

- `80 02` = 640（小端 uint16）
- `E0 01` = 480（小端 uint16）

**结论：** 前 4 字节是 `width(uint16 LE) + height(uint16 LE)`。640×480 是 VGA 高分辨率，符合标题画面预期。

#### 3.2.2 压缩数据流分析

文件头之后是压缩数据。取 `TITLE00A.CMP` 的前若干字节：

```
00 FF  00 FF  00 82  FF  00 FF  00 FF  00 82  FF  ...
```

**观察到的模式：**
- `00 FF` 反复出现 → `00` 可能是命令，`FF` 是参数
- `00 82` 出现 → 同样 `00` 是命令，`82`(=130) 是参数
- `FF` 单独出现 → 可能是"行结束"标记

**推导：**
- 如果 `00` 是"输出 N 个颜色 0"的命令，那么：
  - `00 FF` = 输出 255 个颜色 0
  - `00 FF` = 输出 255 个颜色 0
  - `00 82` = 输出 130 个颜色 0
  - `FF` = 行结束
  - 合计：255 + 255 + 130 = **640 像素** = 正好一行宽度

**这完美吻合！** 第一行全是颜色 0（黑色），符合标题画面顶部黑边的视觉预期。

#### 3.2.3 完整命令集推导

既然 `00` 是"零值连续"，那么自然存在其他命令。对多个 CMP 文件进行字节频率统计和模式分析，结合反汇编验证，得到完整命令集：

![CMP命令集](images/03_cmp_command_reference.png)

| 命令 | 语义 | 后续字节 | 输出 |
|------|------|----------|------|
| `0x00` | 零值连续 | 1字节 count | count × 颜色0 |
| `0x01` | 颜色连续 | count + color | count × 指定颜色 |
| `0x02` | 字面字节 | 1字节 count | 原样复制 count 字节 |
| `0x03` | 字面双字 | 1字节 count | 原样复制 count×4 字节 |
| `0x04` | 双字+1字节 | 1字节 count | 复制 count×4+1 字节 |
| `0x05` | 双字+1字 | 1字节 count | 复制 count×4+2 字节 |
| `0x06` | 双字+字+字节 | 1字节 count | 复制 count×4+3 字节 |
| `0xFF` | 行结束 | 无 | 填充行尾为0，切换下一行 |
| `0x07-0xFE` | 保留 | 无 | 无操作 |

**设计意图分析：**
- `0x00` 零值连续最常用（VGA 图片中颜色 0 = 背景/透明，大面积出现）
- `0x03-0x06` 针对 4 字节对齐的字面数据优化（VGA 帧缓冲区按双字操作是常见优化）
- `0xFF` 行结束使压缩**按行独立**，便于部分绘制和滚动

#### 3.2.4 反汇编验证

为确保命令集完整无误，对 `TESTIMG.EXE`（535KB DOS/4GW 保护模式）进行反汇编：

1. 搜索引用 CMP 文件名字符串的代码 → 定位加载器 `sub_1AD5E`
2. 追踪加载器的调用链 → `sub_1B10C`（Blit包装器）→ `sub_1DA3F`（核心解码器）
3. 分析 `sub_1DA3F`：命令字节通过跳转表分发，共 9 个有效分支

反汇编确认的命令集与上述推导**完全一致**。

### 3.3 IMG 原始图片

游戏目录（非DDT内）有 29 个 `.IMG` 文件。取 `BAG001.IMG`：

- 文件大小：322144 字节
- 前4字节：`FC 07 B1 00` = 1820 × 177
- 验证：`4 + 1820 × 177 = 322144` ✓ 精确吻合

**结论：** IMG = 4字节头(width+height) + 原始8位索引像素，**无压缩**。

### 3.4 XMI 音乐

XMI 是基于 **IFF (Interchange File Format)** 容器的 MIDI 变体：

```
FORM XMI          ← 顶层块
  └── CAT         ← 类别容器 (必须递归进入)
      └── XMID    ← MIDI数据块
          ├── EVNT ← MIDI事件流 (核心数据)
          └── TIMB ← 音色信息 (可选)
```

**关键点：** XMID 嵌套在 CAT 块内，解析 IFF 时必须递归进入 FORM/CAT/LIST 容器，不能只扫顶层。提取 EVNT 块后包装为标准 MIDI 1.0 即可。

### 3.5 TIC 地图瓦片（关键发现）

#### 3.5.1 观察与陷阱

DDT 解包后有 25 个 `.TIC` 文件（PIC001-025.TIC），文件名与 CMP 背景图对应。初步观察：

| 文件 | 大小 | 特征 |
|------|------|------|
| `PIC001.TIC` | 266,240 字节 | 135 种瓦片值，前195字节全0x1F |
| `PIC004.TIC` | 409,600 字节 | 100个64x64块 |

**陷阱：** 直接按 1 字节/瓦片原始数据渲染会产生严重花屏（水平条纹）。原因是 **TIC 数据不是原始瓦片数据，而是 CMP 命令式 RLE 压缩的**。

#### 3.5.2 格式推导

**第一步：块大小推断。** PIC001.TIC = 266,240 字节。尝试 64×64 块（4096 字节/块）：266240 ÷ 4096 = **65 块**，整除。65 = 13×5，得到 832×320 像素的横长地图，比例合理。

**第二步：压缩识别。** 取第3块（偏移8192）的前32字节：

```
00 40 FF 00 40 FF 00 40 FF 00 40 FF 00 40 FF 00 40 FF ...
```

`00 40 FF` 重复9次。对照 CMP 命令集：
- `00 40` = 命令0x00（零值连续），count=64 → 输出64个颜色0（正好一行64像素）
- `FF` = 命令0xFF（行结束）

**结论：每个 64×64 块独立使用与 CMP 完全相同的命令式 RLE 压缩。** 块内无文件头，直接从命令流开始。

#### 3.5.3 格式定义

![TIC格式结构](images/05_tic_format_structure.png)

```
TIC 文件 = N 个连续的 64×64 压缩块
每个块 = 4096 字节固定槽位（压缩数据 + 0填充）
块内 = CMP 命令式 RLE 流（无width/height头，固定64×64）
```

**块排列：** 块按行优先排列为二维网格。块数 N 的因数分解决定地图尺寸：

| 地图 | 块数 | 排列 | 像素尺寸 |
|------|------|------|----------|
| PIC001 | 65 | 13×5 | 832×320 |
| PIC002 | 84 | 14×6 | 896×384 |
| PIC004 | 100 | 20×5 | 1280×320 |
| PIC008 | 120 | 15×8 | 960×512 |

**质数块数地图**（PIC005=59块、PIC007=47块、PIC009=73块等）无法分解为二维矩形，按 N×1 排列为横向线性场景（走廊/通道类关卡）。

#### 3.5.4 配套文件

| 文件 | 大小 | 作用 |
|------|------|------|
| `PICxxx.TIN` | N×2 字节 | 每块一个 uint16 属性表（块类型/地形标记），数量与TIC块数一一对应 |
| `PICxxx.TRM` | 18,468 字节 | 地形事件记录（固定大小） |
| `PICxxx.UNI` | 16,384 字节 | 单位/对象数据（固定大小） |
| `PICxxx.TTY` | 可变 | 场景文本 |
| `FLOOR.DAT` | 432 字节 | 瓦片属性表（18种地形定义） |
| `TRANTAB.DAT` | 65,536 字节 | 256×256 颜色转换表（光照/昼夜效果） |

**TIN 验证：** PIC001.TIN = 130 字节 = 65×uint16，与 PIC001.TIC 的65块一一对应。TIN[0]=0（边界块），TIN[1]=1，TIN[2]=3 等。

## 4. 第四层：实现层 — 解码器与批量转换

### 4.1 CMP 解码器（核心）

![CMP解码流程](images/02_cmp_decoder_flow.png)

```python
import struct
from PIL import Image

def decode_cmp(data: bytes) -> tuple:
    """
    解码 CMP 命令式 RLE 图片
    返回: (pixels_bytearray, width, height)
    """
    width = struct.unpack_from('<H', data, 0)[0]
    height = struct.unpack_from('<H', data, 2)[0]
    output = bytearray(width * height)
    total = width * height

    pos = 4
    out_pos = 0
    row = 0

    while row < height and pos < len(data):
        cmd = data[pos]
        pos += 1

        if cmd == 0x00:
            # 零值连续
            count = data[pos]; pos += 1
            n = min(count, total - out_pos)
            output[out_pos:out_pos+n] = b'\x00' * n
            out_pos += n

        elif cmd == 0x01:
            # 颜色连续
            count = data[pos]; color = data[pos+1]; pos += 2
            n = min(count, total - out_pos)
            output[out_pos:out_pos+n] = bytes([color]) * n
            out_pos += n

        elif cmd == 0x02:
            # 字面字节
            count = data[pos]; pos += 1
            n = min(count, total - out_pos, len(data) - pos)
            output[out_pos:out_pos+n] = data[pos:pos+n]
            out_pos += n; pos += n

        elif cmd in (0x03, 0x04, 0x05, 0x06):
            # 字面双字 + 额外字节 (0x03→+0, 0x04→+1, 0x05→+2, 0x06→+3)
            count = data[pos]; pos += 1
            copy_len = count * 4 + (cmd - 0x03)
            n = min(copy_len, total - out_pos, len(data) - pos)
            output[out_pos:out_pos+n] = data[pos:pos+n]
            out_pos += n; pos += n

        elif cmd == 0xFF:
            # 行结束: 填充当前行剩余为0
            remaining = width - (out_pos - row * width)
            n = min(remaining, total - out_pos)
            output[out_pos:out_pos+n] = b'\x00' * n
            out_pos += n
            row += 1

        # else: 0x07-0xFE 无操作

    # 数据提前结束时填充剩余
    if out_pos < total:
        output[out_pos:] = b'\x00' * (total - out_pos)

    return output, width, height


def cmp_to_png(cmp_path: str, png_path: str, palette: list):
    data = Path(cmp_path).read_bytes()
    pixels, w, h = decode_cmp(data)
    img = Image.new('RGB', (w, h))
    img.putdata([palette[i] for i in pixels])
    img.save(png_path, 'PNG')
```

def batch_extract(game_dir: str, output_dir: str):

### 4.4 TIC 地图解码器

TIC 地图的核心是**复用 CMP 解码器**，但需要按 64×64 块切分并重新排列为二维网格。

```python
import struct
from pathlib import Path
from PIL import Image

BLOCK = 64
BPB = BLOCK * BLOCK  # 4096 字节/块

def decode_cmp_block(data: bytes, width=64, height=64) -> bytearray:
    """解码单个64x64块 (与CMP解码器完全相同的命令式RLE)"""
    output = bytearray(width * height)
    total = width * height
    pos = 0
    out_pos = 0
    row = 0

    while row < height and pos < len(data):
        cmd = data[pos]; pos += 1
        if cmd == 0x00:
            count = data[pos]; pos += 1
            n = min(count, total - out_pos)
            output[out_pos:out_pos+n] = b'\x00' * n
            out_pos += n
        elif cmd == 0x01:
            count = data[pos]; color = data[pos+1]; pos += 2
            n = min(count, total - out_pos)
            output[out_pos:out_pos+n] = bytes([color]) * n
            out_pos += n
        elif cmd == 0x02:
            count = data[pos]; pos += 1
            n = min(count, total - out_pos, len(data) - pos)
            output[out_pos:out_pos+n] = data[pos:pos+n]
            out_pos += n; pos += n
        elif cmd in (0x03, 0x04, 0x05, 0x06):
            count = data[pos]; pos += 1
            copy_len = count * 4 + (cmd - 0x03)
            n = min(copy_len, total - out_pos, len(data) - pos)
            output[out_pos:out_pos+n] = data[pos:pos+n]
            out_pos += n; pos += n
        elif cmd == 0xFF:
            remaining = width - (out_pos - row * width)
            n = min(remaining, total - out_pos)
            output[out_pos:out_pos+n] = b'\x00' * n
            out_pos += n
            row += 1
    return output

def infer_blocks(num_blocks: int) -> tuple:
    """推断块的二维排列 (优先横长比例 1.5-4.0)"""
    best = None
    for bx in range(1, num_blocks + 1):
        if num_blocks % bx == 0:
            by = num_blocks // bx
            ratio = bx / by
            if 1.5 <= ratio <= 4.0:
                score = abs(ratio - 2.6)
                if best is None or score < best[0]:
                    best = (score, bx, by)
    if best is None:
        # 质数块数: 退化为 Nx1 线性排列
        best = (0, num_blocks, 1)
    return best[1], best[2]

def decode_tic_map(tic_path: str, palette: list) -> Image.Image:
    """解码整张TIC地图"""
    tic_data = Path(tic_path).read_bytes()
    num_blocks = len(tic_data) // BPB
    bx, by = infer_blocks(num_blocks)
    map_w, map_h = bx * BLOCK, by * BLOCK

    img = Image.new('RGB', (map_w, map_h))
    pixels = [palette[0]] * (map_w * map_h)

    for b in range(num_blocks):
        offset = b * BPB
        block_data = tic_data[offset:offset+BPB]
        block_pixels = decode_cmp_block(block_data, 64, 64)
        block_x = b % bx
        block_y = b // bx
        for py in range(64):
            for px in range(64):
                x = block_x * 64 + px
                y = block_y * 64 + py
                pixels[y * map_w + x] = palette[block_pixels[py * 64 + px]]

    img.putdata(pixels)
    return img

# 批量解码全部25张地图
for i in range(1, 26):
    tic = cmp_dir / f'PIC{i:03d}.TIC'
    if tic.exists():
        img = decode_tic_map(str(tic), palette)
        img.save(map_dir / f'MAP_PIC{i:03d}_{img.width}x{img.height}.png')
```

**关键验证点：**
- 块2（偏移8192）开头 `00 40 FF` 重复9次 = 9行全黑（每行64像素），解码消耗2402/4096字节，剩余为0填充
- PIC001 解码后瓦片分布：颜色0（背景）占64.5%，蓝绿色（水域）占8.3%，深绿色（森林）占5.7%
- 全部25张地图零失败，目视验证无花屏

## 7. 格式速查卡

### DDT 归档
```
[uint32 LE] N
[N × (12B filename + 4B offset_le)]
[连续数据区]    size[i] = offset[i+1] - offset[i]
```

### CMP 图片
```
[uint16 LE] width
[uint16 LE] height
[命令流, 逐行, 0xFF行结束]
  00 [c]        → c×color0
  01 [c][v]     → c×v
  02 [c]        → 复制c字节
  03-06 [c]     → 复制c×4+(cmd-3)字节
  FF            → 行结束
```

### IMG 图片
```
[uint16 LE] width
[uint16 LE] height
[width×height] 原始8位索引像素
```

### PAL 调色板
```
[256 × 3B] RGB6,  v8 = (v6<<2)|(v6>>4)
```

### XMI 音乐
```
IFF FORM/CAT 递归容器, 提取 EVNT 块 → 标准MIDI
```

### TIC 地图瓦片
```
[N × 4096B] 连续64x64压缩块
  每块 = CMP命令式RLE流 (无width/height头, 固定64x64)
  块排列 = 行优先二维网格 (因数分解推断, 质数退化为Nx1)
配套: TIN(每块uint16属性) / TRM(地形事件) / UNI(单位数据)
```

## 8. 关键洞察总结

1. **归档格式极简：** DDT 只有"文件数 + 文件名偏移对 + 连续数据"三部分，无压缩、无校验。目录项只存偏移不存大小是最容易踩的坑。

2. **CMP 压缩的设计智慧：** 命令式 RLE 而非简单 RLE。`0x00` 零值连续专门优化 VGA 背景色（颜色0通常占 30-60% 像素），`0x03-0x06` 双字复制针对 32 位 CPU 优化，`0xFF` 行结束支持部分刷新。

3. **TIC 复用 CMP 压缩器：** 地图瓦片不是原始数据，而是每个 64×64 块独立用与 CMP 完全相同的命令式 RLE 压缩。直接按 1 字节/瓦片渲染必然花屏。识别线索：块内开头出现 `00 40 FF` 重复模式（=64个颜色0+行结束，正好一行）。

4. **分析顺序很重要：** 先调色板（5分钟）→ 再 CMP（核心）→ 其余顺势。如果先啃 CMP 而没有调色板，解码出来的索引像素无法目视验证，会大幅拖慢迭代速度。

5. **单文件验证优先：** 始终用 `TITLE00A.CMP`（文件名语义明确、640×480 全屏、内容可预期）作为验证锚点，而不是随机挑文件。首行 640 像素全黑的数学吻合是算法正确的第一个强信号。

6. **反汇编是最终仲裁者：** 静态分析压缩流可以推导出 90% 的命令集，但 `0x03-0x06` 的微妙差异（双字+额外字节）只有反汇编才能 100% 确认。对于自研格式，**反汇编不是可选项，是必需的验证步骤。**

## 2. ChiTon UNIT v2.0 容器格式

### 2.1 统一头部

几乎所有资源文件（.TLK/.ICO/.FIG/.BKS/.MPS/.MON/.ITM/.WP/.NPC/.OBS/.EFC/.EVT/.MID/.SND/.ANM）都以相同的16字节头部开始：

```
偏移  长度  说明
0x00  16    "ChiTon UNIT v2.0" (ASCII, 无结束符)
0x10  可变  各格式自定义头部字段
```

### 2.2 各格式头部字段

| 文件 | 0x10 | 0x12 | 0x14 | 0x16 | 0x18 | 说明 |
|------|------|------|------|------|------|------|
| EAGLE.TLK | 1 | 55 | 0 | - | 文本大小 | 对话文本 |
| EAGLEANM.TLK | 1 | 59 | 0 | - | 文本大小 | 动画对话 |
| EAGLE.ICO | 16 | 16 | 0 | 0 | 0 | 图标尺寸16x16 |
| EAGLE.FIG | 120 | 72 | 40 | 40 | 调色板 | 界面图形 |
| EAGLE.BKS | 0 | 0 | 0 | 0 | 2(组数) | 背景包偏移表 |
| EAGLE.MID | - | - | - | - | - | XMI音乐(IFF) |
| EAGLE.SND | - | - | - | - | - | WAV音效(RIFF) |

### 2.3 末尾索引表

所有ChiTon文件末尾都有索引表，格式为：

```
每条目4字节:
  uint16  flag    (条目类型/标志)
  uint16  offset  (相对于数据区的偏移)
```

例如：
- EAGLE.ICO: 129个条目，flag=0x000B
- EAGLE.FIG: 6个条目，flag=0x0000/0x0001

## 4. 图片格式逆向（IDA Pro 7.6 反汇编确认）

### 4.1 逆向方法论

通过 **IDA Pro 7.6** 反汇编 `EAGLE.EXE`（DOS/4GW保护模式，767KB），定位到CONDOR引擎的图像解码函数族：

| 函数 | 地址 | 功能 |
|------|------|------|
| `sub_122F0` | 0x122F0 | ChiTon UNIT文件加载器 |
| `sub_12410` | 0x12410 | 按索引条目读取数据 |
| `sub_50129` | 0x50129 | **BKS瓦片实际绘制函数**（含写入） |
| `sub_5050D` | 0x5050D | BKS瓦片解析器（无写入，用于碰撞检测） |
| `sub_5056F` | 0x5056F | FIG稀疏数据复制函数 |
| `sub_505B0` | 0x505B0 | FIG带偏移的稀疏数据复制 |

### 4.2 EAGLE.BKS（背景/砖块包）—— 完全破解

**大小**: 5.4 MB  
**ChiTon条目数**: 41个背景组  
**每个条目结构**: 偏移表(0x2000字节=2048个uint32) + 像素数据区

#### 4.2.1 两层索引结构

```
EAGLE.BKS (ChiTon UNIT v2.0)
├── 16字节头部 "ChiTon UNIT V2.0"
├── 数据区 (41个背景组)
│   ├── 组0: [偏移表 0x2000字节] [像素数据]
│   ├── 组1: [偏移表 0x2000字节] [像素数据]
│   └── ...
└── 末尾索引表 [uint16 条目数=41] [41×uint32 结束偏移]
```

**组内瓦片查找**:
- 偏移表位于组起始，共2048个uint32（0x2000字节）
- 瓦片ID的高字节低3位用于调色板/层选择（`and ah, 7`）
- 瓦片数据指针 = 组起始 + 0x2000 + 偏移表[瓦片ID]

#### 4.2.2 命令式RLE压缩格式（sub_50129确认）

每个瓦片数据以 **header(uint16 LE)** 开始，表示从目标缓冲区末尾的偏移量：
```
target = buffer_size - header   (buffer_size=64000=320×200)
```

可选额外偏移：若下一字节最高位为0，读取uint16 BE作为额外偏移，`target -= extra`。

**命令流**（3种命令，由命令字节最高2位区分）:

| 命令范围 | 类型 | 格式 | 说明 |
|----------|------|------|------|
| `0x00-0x7F` | 跳过(透明) | `颜色 重复次数` | `add edi, eax` 仅移动指针不写入，颜色值被忽略 |
| `0x80-0xBF` | 复制原始数据 | `长度(低6位) 原始数据...` | `rep movsb` 复制长度字节 |
| `0xC0-0xFF` | 填充颜色 | `次数(低6位) 颜色` | `rep stosb` 填充次数个颜色 |

**结束标记**: `00 00`（颜色0 + 重复次数0）

#### 4.2.3 提取结果

- **41张背景图像**，尺寸约320×80~95像素（屏幕下半部分）
- 内容包括：水面波纹、地面纹理、山石、建筑基座等
- 输出目录: `extracted/SHENDIAO_神雕侠侣/03_bks_backgrounds/`

### 4.5 调色板（真实调色板定位完成）★

BKS/FIG/ICO/NPC/MON/OBS/MPS 均使用 8 位颜色索引，EXE 内**没有**独立的静态 768 字节调色板。用 IDA 追踪 VGA DAC 写入（`out 3C8h/3C9h`）定位到场景结构 `dword_97864`：

- 该结构在 `sub_*` 中分配，大小 `0xB63 = 2915` 字节；其 `+0xB1B` 处存放调色板指针，反汇编（行 3080–3081）证明该指针 = 结构基址 + `0x251`；
- 整个结构在切场景时整体落盘为 **`EAGLEN.DAT`**（2915 字节，即退出/存档快照）。

因此**真实调色板 = `EAGLEN.DAT[0x251 : 0x251+768]`，共 768 字节、256 色 × RGB，6 位 DAC**（每通道 0–63），转 8 位：`v8 = v6 * 255 // 63`。实测 distinct=64（场景实际用色）。共享库 `condor_format.load_palette()` 已实现读取；全部 NPC/MON/EFC/ITM/WP/MPS 已用此调色板重染为真彩，与 DOSBox-X 实机截图一致。

> 备注（隐患）：CONDOR 引擎另有 `npal/dpal/xpal` 多套调色板，`EAGLEN.DAT` 内联的是**最后一次存档场景**那一套；若个别场景偏色，需再追 DAC 写入点（结构内偏移 0xB1B，见反汇编行 3081/9726）切换到对应场景调色板。

### 4.6 EAGLE.NPC（角色精灵）—— 完全破解 ★

`EAGLE.NPC`（5.2 MB）是ChiTon容器，含 **331 个条目**（其中327个有效角色/物件，2个保留空条目），共解出 **4383 帧**精灵动画。

#### 4.6.1 离屏缓冲区与关键常量（破解的核心）

游戏虽以 VGA Mode 13h（物理 320×200）显示，但引擎先绘制到一块**离屏缓冲区**，其行宽（pitch）为 **400 字节**而非320。该常量由初始化函数 `sub_10210` → `sub_4FD32` 写入：

```asm
; sub_10210
mov word ptr [eax],   190h   ; 缓冲区宽度  = 0x190 = 400  → word_95848
mov word ptr [eax+2], 228h   ; 缓冲区高度  = 0x228 = 552
push 190h
call sub_4FD32               ; 内部 mov ax,13h; int 10h（设置320×200物理模式）
                             ; 并 mov dword_95844, eax（缓冲区基址）
```

> **关键教训**：BKS 命令流中的"跳过偏移"是相对**线性字节地址**的增量，换行由 pitch 决定。若误用物理行宽320去解释，跳过量（如394）会导致像素横向错位到257列宽；用正确的 pitch=400 解释，同一数据恰好逐行收束成18列宽的角色（见下图）。

![pitch对比图](images/06_npc_pitch_comparison.png)

*左：误用pitch=320，像素散成257列水平线条；右：正确pitch=400，收束为完整角色。验证：跳过量394 = 400−52+46，389 = 400−54+43，逐行严丝合缝。*

绘制目标基准（`sub_138C0` → `sub_50294`）：

```asm
; sub_138C0 入口 arg_0 = 0（调用者 sub_15930 传入）
add [ebp+arg_0], 0FA00h       ; +64000（前后台缓冲区分界 = 400×160）
...
mov eax, [ebp+var_10]         ; 64000
add eax, 0C90h                ; NPC层目标 = 64000 + 3216 = 67216
push eax                      ; arg_0 of sub_50294
```

即 **arg0 = 67216**，缓冲区总大小 = 400×552 = 220800。

#### 4.6.2 NPC条目内存布局（`sub_1BD70` 确认）

```
偏移      长度      字段
+0x00     uint16    w（角色框宽，恒为36）
+0x02     uint16    h（角色框高，恒为64）
+0x04     uint16    param（恒为96=0x60）
+0x06     4×uint32  方向偏移表 dir[4]      → 结构字段 +0x2F
+0x16     32×uint32 帧偏移表 frame[32]     → 结构字段 +0x33
+0x96     ...       数据区（方向静态图 + 帧动画）→ 结构字段 +0x37
```

- 数据区前 `frame[0]` 字节为**方向数据区**（4方向静态图）；其后为**帧动画区**。
- 第 k 帧数据 = `条目 + 0x96 + frame[k]`，长度 = `frame[k+1] − frame[k]`（末帧长度到条目尾）。
- **帧表两种布局**：
  - **玩家型**（如entry2）：32帧全有效 = 4 朝向 × 8 帧行走循环；
  - **NPC型**：仅 frame{0,4,8,12,16,20,24,28} 有效（8朝向各1帧静态），其余为4字节空帧（仅 header+结束标记）。
- 绘制时由角色状态字 `var_4` 选择：bit5=1 走方向表（索引=var_4&3），bit5=0 走帧表（索引=var_4&0x1F）。

#### 4.6.3 单帧 = 双 BKS 块（`sub_50294` 确认）

一帧数据由**两个BKS块**顺序组成：第一块**标准绘制**角色本体，遇 `00 00` 结束；第二块以**混合模式**叠加高光/阴影。若第一块 header=0 表示无本体（纯特效层，全库仅27帧，单独渲染为空属正常）。

```
块1(标准):  header(u16LE) [header=0xFFFF时的多级偏移，本库不出现]  命令流…  00 00
块2(混合):  header(u16LE) [下一字节<0x80 时存在 u16 大端额外偏移]  命令流…  00 00
```

命令编码（两块相同，绘制语义不同），起始指针 `edi = arg0 − header − extra`：

| 命令字节 | 类型 | 语义 |
|---------|------|------|
| `cmd < 0x80` | 跳过 | 再读1字节 nxt，线性跳过 `(cmd<<8) \| nxt`；为0即本块结束 |
| `0x80–0xBF` | 复制 | 长度 = `cmd & 0x3F`，随后逐字节为像素 |
| `0xC0–0xFF` | 填充 | 次数 = `cmd & 0x3F`，再读1字节为填充色 |

**标准块**：复制=直接写入，填充=直接写常量。
**混合块**（`loc_50337/loc_50362`）：对每个目标像素做"低4位饱和加法、保留高4位"：

```python
def blend(src, dst):                 # src=源像素(完整8位), dst=目标像素
    r = (src + (dst & 0x0F)) & 0xFF  # 完整源字节 + 目标低4位
    if   r & 0x80: r = 0            # ≥128 → 0
    elif r & 0xF0: r = 0x0F         # 16..127 → 饱和15
    return r | (dst & 0xF0)         # 0..15保持；保留目标高4位
```

#### 4.6.4 解码算法（从结果倒推的最短路径）

1. 按 §2 解析ChiTon容器得到331个条目；
2. 对每个条目读 w/h 与32项帧表，跳过 ≤6 字节的空帧；
3. 对每帧建立 400×552 线性缓冲区，`edi = 67216 − header`；
4. 顺序执行块1标准命令流，再执行块2混合命令流；
5. 扫描非零像素的最小外接矩形裁剪，按8位索引写P（灰度调色板便于预览）。

### 4.8 EAGLE.MPS 等距地图 —— 完全破解 ★

`EAGLE.MPS` 含 **168 张地图**（民宅/杂货铺/客栈/渡口/庙/岛/山脚/宫/村/大厅/地道/城池/府第…），BKS tileset 17 套(0–16)、OBS 物体 tileset 6 套(0–5)。最终批量导出 `16_mps_maps/`（168 张 PNG + manifest）。

#### 4.8.1 条目头与 RLE 解压

- 条目头长 **0x827**：`@0x04` Big5 地图名；`@0x0D` BKS tileset 号、`@0x0F` OBS tileset 号；`@0x11` 宽 W、`@0x13` 高 H、`@0x19` tile 总数 `nt=W*H`（均 u16）。
- `@0x827` 起为 **word 型 RLE 流**，解压到 **3·nt 个 word**：
  - word `<0x8000`：直接取该值；
  - word 最高位 bit15=1：低 15 位 = 重复次数，**下一个有符号 word** = 填充值；
  - 遇 `0xFFFF` 结束，剩余补 0。

#### 4.8.2 三个“分离平面”，不是 interleaved（纠错①）

解压结果必须 reshape 成**三个独立的 H×W 平面**，而非 `(H,W,3)`：IDA 层切换 `loc_143C3` 中数据指针 `var_30 += 2*[0x24D]`，而 `[+0x24D]` = 头 0x19 = nt。故：

```
平面0 = word[0    : nt]      # 地面/顶面，只用 BKS 画
平面1 = word[nt   : 2*nt]    # 物体/立面，用 OBS 画
平面2 = word[2*nt : 3*nt]    # 物体/立面，用 OBS 画
```

**平面 0 只画 BKS、绝不画 OBS**（纠错④）：平面 0 的属性 bit13 全 0，走 `loc_13CC6` 只调 `sub_50129`（BKS 单块覆盖写）；物体/立面只在平面 1/2 用 `sub_50294`（OBS 混合）。早期对平面 0 同时画 OBS，会在渡口等处产生大片悬浮崖壁网格。

#### 4.8.3 tile word 位域

```
低11位 &0x7FF = tileset 图块索引
高5位属性： bit11 0x0800=透明/存在不画 ; bit13 0x2000=特殊错位物体 ;
           bit14 0x4000 ; bit15 0x8000
```

#### 4.8.4 等距 45° 投影（纠错②，核心）

地图不是正交网格。由 `sub_138C0` 地址步进联立：屏幕行 `var_C += 0x1900(=6400=16*400)`、列 `var_10 += 0x20(=32)`；数据指针行 `+=2(W+1)`、列 `-=2(W-1)`。设数据格 `(dr,dc)`、屏幕格 `(sr,sc)`，由 `dr=sr-sc、dc=sr+sc` 反推：

```
屏幕像素  x = 16*(dc - dr)
          y =  8*(dr + dc)        # 一个 cell 菱形宽32、高16
沿 dr 方向屏幕步进 (-16,+8)，沿 dc 方向 (+16,+8)
```

绘制按 **`dr+dc` 升序**（远→近 painter 算法），后画的近格盖住远格。

#### 4.8.5 tileset 取块与“全局固定相位=32”（纠错③，最隐蔽）

- tileset 条目：前 `0x2000=2048` 个 uint32 是偏移表（对应 11 位索引），其后是图块数据；图块 idx 字节段 = `[0x2000+tab[idx], 0x2000+tab[下一个更大非零tab])`。
- 图块用 BKS 原语渲染到 pitch=400 离屏缓冲，cell 锚点 U=0 对齐到该格屏幕 `(x,y)`，粘贴位置 = `(x-anchor_x, y-anchor_y)`。
- **锚点 x 相位必须全局固定 = 32（=列步长 0x20），不能逐块自适应**：曾尝试“每块选最紧凑相位”，虽让图案不被 400 边界切开，却把 U=0 锚点甩到 x≈392，导致家具整体错位到菱形左侧外。枚举证明：**ph=32 时跨界块（如 OBS idx38）从 400 宽恢复为 80 宽且锚点合理，其余块结果与 ph=20 完全一致**，BKS/OBS 通用。库常量 `MAP_ANCHOR_PHASE=32`，`make_tile_sprite(..., force_phase=32)`。

> 方法论（从结果倒推）：分离平面 → 只给平面 0 画 BKS → 用地址步进联立解出等距公式 → 全局枚举锚点相位取“所有块紧凑且锚点合理”的公共值。批量导出器 `scripts/164_export_all_maps.py`，原型 `158_render_iso_final.py`。

## 5. 音乐格式逆向与MIDI修复

### 5.1 XMI格式分析

`EAGLE.MID`（83KB）采用 **XMI（eXtended MIDI）** 格式，封装在ChiTon UNIT容器中。XMI是Origin Systems开发的MIDI扩展格式，使用IFF容器：

```
EAGLE.MID (ChiTon UNIT v2.0)
└── 16首音乐, 每首结构:
    FORM XDIR
    ├── INFO (曲目信息)
    └── CAT XMID
        └── FORM XMID
            ├── TIMB (乐器配置)
            └── EVNT (MIDI事件数据)
```

### 5.2 关键发现：XMI事件编码与标准MIDI的差异

**问题根因**: 早期提取的MIDI文件没有声音，因为XMI的EVNT事件编码与标准MIDI有本质区别：

| 特性 | 标准MIDI | XMI EVNT |
|------|----------|----------|
| Delta Time位置 | 事件**前面** | 事件**后面** |
| Program Change后delta | 总是有（可为0） | delta=0时**省略** |
| Meta事件后delta | 总是有（可为0） | delta=0时**省略** |
| Note On/Off后delta | 总是有 | **总是有** |

**XMI事件序列示例**:
```
FF 58 04 04 02 18 08   ; Meta TimeSig (delta=0, 省略)
FF 21 01 00              ; Meta Port x8 (delta=0, 省略)
FF 59 02 00 00           ; Meta KeySig (delta=0, 省略)
C2 5F                     ; Program Change ch=2 (delta=0, 省略)
C3 62                     ; Program Change ch=3 (delta=0, 省略)
99 52 56                  ; Note On ch=9 note=0x52 vel=0x56
19                         ; delta time = 25 (事件后面!)
92 2C 64                  ; Note Off ch=2
83 1B                      ; delta time = 411 (可变长度: (0x83&0x7F)<<7 | 0x1B)
93 50 3C                  ; Note On ch=3
19                         ; delta time = 25
```

### 5.3 状态机转换器

正确的转换方法是使用**状态机**:
1. **EVENT状态**: 读取MIDI事件
   - Note On/Off/CC/Pitch (3字节事件) → 记录事件，切换到DELTA状态
   - Program Change/Channel Pressure (2字节事件) → delta=0，保持EVENT状态
   - Meta/SysEx → delta=0，保持EVENT状态
2. **DELTA状态**: 读取事件后面的delta time（单字节0x00-0x7F或可变长度0x80-0xFF开头），更新上一事件的delta，切换回EVENT状态
3. 输出标准MIDI: delta time → event

### 5.4 提取结果

- **16首MIDI音乐**，总计 **21,029个Note On事件**
- 时间分度: 192 ticks/quarter note
- 格式: 标准MIDI格式0（单轨道）
- 输出目录: `06_music_mid/track01_v4.mid` ~ `track16_v4.mid`

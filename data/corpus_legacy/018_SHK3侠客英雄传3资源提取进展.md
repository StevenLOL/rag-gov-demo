## 2. SuperYin（.YIN）归档容器 —— 决定性突破

### 2.1 三个归档

| 文件 | 大小 | 条目数 | 内容 |
|------|------|--------|------|
| `PUBDATA.YIN` | 52,032,958 | 255 | 公共资源：背景、头像、PAL、特效、UI |
| `ssFIGHT.YIN` | 161,289,444 | 2677 | 战斗数据：敌人 PLK/BLK、武器、PAL、FLC |
| CD `Shk3.yin` | 162,588,563 | 1213 | 地图/事件：CEL、BLKMAN、MAP、FLG |

### 2.2 容器结构（★ 偏移表是**绝对文件偏移**）

```
偏移                    长度        内容
0x00                    2           count (LE16)
0x02                    13 × count  文件名表（每条 13 字节，加密）
0x02 + count*13         4 × count   大小表（LE32）
0x02 + count*13 + count*4   4×count 偏移表（LE32）★绝对文件偏移
...                                 数据区
```

- **文件名加密**：`加密字节 = 原始字节 + 0x64`，解密时 `- 0x64`（& 0xFF）。
- **★偏移表里的数值就是文件内绝对偏移**，提取第 i 个文件直接：
  ```python
  data = blob[ off[i] : off[i] + size[i] ]
  ```
  **不要再加任何 data_start**。

### 2.3 健壮的文件名解密（关键坑）

不同归档的 13 字节填充值不一样：
- `PUBDATA.YIN`：填充原始 = `0x64`，解密后 = `0x00`；
- `ssFIGHT.YIN`：填充原始 = `0x00`，解密后 = `0x9c`。

如果只 `rstrip('\x9c')`，ssFIGHT 会解出 `PLK\x9c\x9c` 这种脏扩展名，把同一类文件拆到十几个目录。**正确做法是只保留可打印 ASCII 前缀**：

```python
def decname(raw):
    dec = bytes((x - 0x64) & 0xFF for x in raw)
    return bytes(c for c in dec if 32 <= c < 127).decode('latin1')
```

修正后 ssFIGHT 干净分类为：`PAL 1051 / PLK 963 / FLC 307 / BLK 312 / BIN 42 / NUM 2`。

### 2.4 容器解析参考代码

```python
import struct
def unpack_yin(path):
    d = open(path, 'rb').read()
    count = struct.unpack('<H', d[0:2])[0]
    names = [decname(d[2+i*13:2+i*13+13]) for i in range(count)]
    sb = 2 + count*13
    sizes = [struct.unpack('<I', d[sb+i*4:sb+i*4+4])[0] for i in range(count)]
    ob = sb + count*4
    offs  = [struct.unpack('<I', d[ob+i*4:ob+i*4+4])[0] for i in range(count)]
    return [(names[i], d[offs[i]:offs[i]+sizes[i]]) for i in range(count)]
```

## 3. EXE 真相：是 32 位保护模式，不是 16 位

`SHK3_.EXE`（411,671 字节）的 MZ 头中 `e_lfanew = 0x2410`，指向的签名是 **"LE"**，且文件内含字符串 `PMODE/W v1.`。

- 它是 **32 位保护模式程序**（用 PMODE/W DOS 扩展器），**不是 16 位**。
- 因此按 16 位去找 `int 10h`、VGA 寄存器交叉引用会一无所获。
- 用 IDA 以 **LE 加载器**打开；capstone 直接反汇编 obj1 与 IDA 的 VA 之间存在约 **0x1BF 的固定偏移差**，分析地址一律以 IDA VA 为准。

## 4. 背景渲染：BIN = 直接像素，无压缩

### 4.1 BIN 结构

每张战斗背景是一个 `.BIN`：

```
偏移   长度   内容
0x00   2      宽度 (LE16) = 320
0x02   2      高度 (LE16) = 200
0x04   64000  原始 8bpp 像素（逐行，pitch=320）
```

反编译中背景解码 `sub_36AD1` 直接：
```c
qmemcpy(&unk_A0000, BIN + 4, 0xFA00);   // 0xFA00 = 64000
```
**没有任何 RLE / 压缩**，4 字节头之后整块拷贝到 VRAM。

### 4.2 背景 PAL 的 DAC 映射

每张背景配一个 `.PAL`（192 字节 = 64 色 ×3），这 64 色被送到 DAC 的 **192–255**：

```c
// sub_36A44：把 PAL 字节逐个写 0x3C9，硬件取低 6 位
```

VGA 硬件把 6bit 经 3C9 输出，软件还原成 8bit：
```python
r8 = (v << 2) | (v >> 4)
```

![BG01 战斗背景](../extracted/SHK3_侠客英雄传3/backgrounds_final/BG01.png)

![EVBG 事件背景](../extracted/SHK3_侠客英雄传3/backgrounds_final/EVBG01.png)

修正偏移后，22 张 BG 与 20 张 EVBG **一次性全部正确**（草地、树干、远山、天空颜色均与真机一致）。

## 4.5 ★ 背景上屏真相：BIN 静态底图 + FLC 环境动画

重新反编译背景加载函数 `sub_23892` 后确认，战斗背景不是 BIN 直接全屏，而是 **BIN 底图 + 同名 FLC 动画**两层：

1. `sub_34E1D("BG%02d.BIN", ..., dword_98238, ...)` 把 BIN 读入缓冲，`dword_A7EB0 = dword_98238 + 4`（像素起点）；
2. 读入同名 PAL；
3. 对战斗背景（非 EVBG）再打开 `BG%02d.FLC`，主循环不断 `sub_39D9B(flc, &unk_A0000)` 把 FLC 逐帧解码到 VRAM；
4. 战斗初始化在开场演示后用 `sub_36AD1(dword_A7EB0)` 把 BIN 整块铺成战场底图。

即 **BIN 是静态战场底图，FLC 负责天空云、飞鸟等环境动画与开场镜头**。

### 4.5.1 FLC 帧的链式定位（不是搜索 F1FA）

FLC 帧由帧头 size 字段链式定位（`sub_39A5D`）：从 128 字节文件头之后读 16 字节帧头，`位置 += size`。

- 真帧 magic = **F1FA**（字节 `FA F1`）；
- **F100 路径块**（字节 `00 F1`，体内含 `"C:\SHK3\SYS\DATA\BG01.FLC"` 字符串）被整体跳过——它不是帧。直接全文搜索 F1FA 会把它之后的位置误判成帧。

### 4.5.2 帧内 chunk 类型表（`sub_41598`）

帧头 `+6` = chunk 数（u16），chunks 自 `+16` 起；每个 chunk：size(u32)@0、type(u16)@4、body@6。

| type | 处理函数 | 含义 |
|------|----------|------|
| 0x0F | `sub_41880` | **LC 全帧**：固定 **56 段**线性紧密拼接；每段包 count(u8)：<128 run（读 1 色 memset）、≥128 literal（取负 count，qmemcpy）|
| 0x07 | `sub_41690` | **SS2 delta**：2 像素组在同一扫描行水平排列；目标 `dest[x, y=v18+v16]`，负 signed word 累加行偏移 |
| 0x0C | `sub_41639` | 行级 delta：startRow(u16)、nrows(u16)，每行包 [xoff][cnt][data] |
| 0x10 | `sub_418A8` | 全屏原始块：qmemcpy 64000 |
| 0x0D | `sub_418B6` | 清屏 memset 0 |
| 0x04 | `sub_417DB` | **调色板包（6bit）**：每个颜色字节先 **>>2** 再送 3C9 |
| 0x0B | `sub_41759` | 调色板包（8bit，直送） |
| 0x12 | — | 标签/路径信息，跳过 |

### 4.5.3 首帧只画 320×56 天空

BG01.FLC 第一帧 = 路径块(skip) + 0x04 调色板 + 0x0F LC。严格按 `sub_41880` 解码 LC 得 **17920 像素 = 320×56**，即首帧只更新屏幕顶部 56 行天空（云），地面留待 BIN/后续帧。

![FLC 首帧天空](../extracted/SHK3_侠客英雄传3/_geo/flc0_lc320x56.png)

0x04 调色板是 packet 格式（u16 包数，随后 [skip u8][cnt u8]，cnt=0 表 256 色 + 768 字节），颜色字节 **>>2 得 6bit**，再 `(v<<2)|(v>>4)` 扩 8bit。

### 4.5.4 22 个 FLC 完整环境背景

播放每个 BG FLC 的全部帧、取内容最完整帧，得到 22 张比 BIN 更丰富的环境画面（含飞鸟、云层、开场镜头）：

![FLC 环境背景联系表](../extracted/SHK3_侠客英雄传3/flc_backgrounds/_contact.png)

存于 `flc_backgrounds/BG01-22.png`。它们与 BIN 一样是线性 320×200、水平连续，几何上同样不存在错位。

## 5. PLK 容器：帧表 + 重定位

### 5.1 PLK 在内存中的结构（加载函数 `sub_239F1`）

```
偏移        内容
0x00        count (u8) —— 帧数
0x01        count × u32 帧偏移表
0x01+4*count 数据区
```

加载时，程序在**源数据上原地**把每个帧偏移 `+= 数据区基址`，重定位成绝对帧指针：
```c
a1[0] = count;
base  = a2 + 1 + 4*count;
for (i...) frame_ptr_table[i] += base;   // 原地重定位
*(DWORD*)(a1 + 2) = a2 + 1;              // 指向重定位后的指针表
```

解析参考：
```python
def plk_frames(d):
    count = d[0]
    offs = [struct.unpack('<I', d[1+i*4:1+i*4+4])[0] for i in range(count)]
    b = 1 + 4*count
    return [d[b+offs[i]:(b+offs[i+1] if i+1 < count else len(d))]
            for i in range(count)]
```

### 5.2 帧头

每一帧：
```
偏移  长度  内容
0x00  2     魔数 69 59（blit 内 lodsw 后 cmp ax, 0x5969）
0x02  2     宽度 w (LE16)
0x04  2     高度 h (LE16)
0x06  可变  命令数据
```

`sub_1B6C8` 证实宽在 +2、高在 +4。

## 6. ★ 核心 blit 算法（`sub_35E68`）—— 完整保存

绘制函数签名：`blit(eax=帧指针, edx=目标地址, ebx=pitch=320)`。
它是一个**线程化解释器（threaded interpreter）**，命令分两个阶段。

### 6.1 全局行状态

| 变量 | 含义 |
|------|------|
| `dword_52F7C` | 总行数 = h |
| `dword_52F78` | 外层行预算 |
| `dword_52F70` | 行内剩余 |
| `dword_52F74` | run / 块剩余 |
| `dword_52F68 / 52F6C` | 初始值（行宽 w） |

简单调用（`sub_13900`）初始化：`52F7C=h、52F74=w、52F6C=w`，其余 0。

### 6.2 阶段 1：帧开头的行级 skip

| 命令 | 操作 |
|------|------|
| `0` | EOF |
| `1 n` | 目标下移 n 行（`edx += pitch*n`） |
| `2` | skip 1 字节 |
| `3` | skip 2 字节 |
| `4 n` | skip n 个源字节 |

### 6.3 阶段 2（跳转表 `jpt_35E1E`，6 个 case）

| case | 位置 | 操作 |
|------|------|------|
| 0 | `off_19DE9` | 特殊（帧末/填充，正常精灵用不到） |
| 1 | `loc_35F37` | 垂直 skip n 个空行，并重置行宽 |
| 2 | `loc_35F64` | 水平透明 skip n（`edi += n`） |
| 3 | `loc_35FBD` | **run**：`lodsb count; lodsb color; rep stosb` |
| 4 | `loc_3602B` | **原始块**：`lodsb count; rep movsb` |
| 5 | `loc_360AF` | **换行**：行数 -1、`目标 += pitch`、重置行宽 |

> 第二同构变体在 `sub_360DA`，结构完全一致，差异是翻转 / 透明模式。

### 6.4 可复现的帧解码参考实现

```python
def decode_frame(f):
    import struct
    w, h = struct.unpack('<HH', f[2:6])
    canvas = [[0]*w for _ in range(h)]
    x = y = 0; j = 6
    while j < len(f):
        cmd = f[j]; j += 1
        if   cmd == 0: break
        elif cmd == 1: n = f[j]; j += 1; y += n; x = 0
        elif cmd == 2: n = f[j]; j += 1; x += n
        elif cmd == 3:
            n, c = f[j], f[j+1]; j += 2
            for k in range(n):
                if 0 <= x+k < w and y < h: canvas[y][x+k] = c
            x += n
        elif cmd == 4:
            n = f[j]; j += 1
            for k in range(n):
                if 0 <= x+k < w and y < h: canvas[y][x+k] = f[j+k]
            j += n; x += n
        elif cmd == 5: y += 1; x = 0
    return canvas, w, h
```

> 注意：`0x32 / 0x33 / 0x34 / 0x35` 这些字节**不是命令**，它们是 RLE 数据里的计数 / 颜色。全代码扫描没有任何函数把它们当操作码——真实命令只有上述 0–5。

## 10. 错误复盘：早期为什么全错，后来怎么对的

### 10.1 根因一：偏移表被误当成「相对偏移」（最致命）

早期假设偏移表是相对数据区的，提取时 `data = blob[data_start + off[i] : ...]`，自作主张加了 `data_start = 5357`。

结果所有文件**整体错位**，并引发一连串假象：
- 绿草成品红、颜色系统性偏移；
- 画面左 25% 像是被挪到了右边；
- 底部出现黑条、高度像多出 10%。

**真相**：偏移表是**绝对文件偏移**，一个字节都不用加。修正后 42 张背景、72 头像一次性全对——之前死磕的「RGB 通道排列」「水平循环移位」「换 LOADING PAL」全是错位的次生症状，根本不存在。

> 教训：**先把容器的偏移语义核实清楚（最小索引是否为 0、最大偏移+size 是否等于文件长），再谈像素和调色板。** 容器错位时，任何像素层的猜测都是徒劳。

### 10.2 根因二：把 32 位程序当 16 位分析

EXE 实际是 LE + PMODE/W 的 32 位保护模式程序。按 16 位找 `int 10h` / VGA xref 全部扑空；capstone 反汇编 obj1 与 IDA VA 又有 0x1BF 误差，导致按错地址分析。改用 IDA 以 LE 加载后，blit / PAL 函数全部对上。

### 10.3 根因三：把数据字节当命令

一度把 `0x32–0x35` 当成 PLK 操作码，解出来全是雪花。全代码扫描证明没有任何函数引用它们——它们是 RLE 的计数 / 颜色；真实命令只有阶段 1 的 0–4 和阶段 2 的 0–5。

### 10.4 根因四：文件名清理不彻底

ssFIGHT 的填充解密后是 `0x9c`，只 `rstrip` 会留下脏扩展名、把 963 个 PLK 拆到 6 个目录，造成「还有 798 个未知 PLK（可能是身体）」的错觉。改成「只保留可打印 ASCII 前缀」后，PLK 总数仍是 963，并不存在隐藏身体。

### 10.5 「怎么就蒙对了」

不是蒙，是把权威来源换成了**反编译本身**：
1. 用 IDA 看背景解码 `qmemcpy(..., 0xFA00)` → 确定无压缩、尺寸 320×200；
2. 看 PAL 写 3C9 的起始参数 → 确定各素材的 DAC 段；
3. 逐 case 读 blit 跳转表 → 得到确定的命令语义；
4. 用「敌人 PAL A @DAC128」一次渲染出银甲红披风武将，验证整套映射成立。

## 11. 可复现流程（端到端）

1. **解包三个 YIN**（§2.4），文件名用可打印 ASCII 过滤（§2.3），偏移按绝对偏移切片。
2. **背景**：`BIN+4` 取 64000 字节，reshape 320×200；同名 `PAL`（64 色）放 DAC192，6→8bit。
3. **头像**：`HEAD.PLK` 帧逐个解码，HEAD.PAL 放对应段。
4. **敌人**：`ENnnSTD/DEF` 用 `ENnnA.PAL` @DAC128；`STDG` 与 BLK `B/C/E` 用 56–63 灰度；BLK `03` 用 PAL A @128。
5. **地图角色**：CD `BLKMAN.YIN` 纯偏移表，每块跳过 2 前缀解 24×40 帧，`AO00.PAL` @DAC192。
6. **武器**：`AxxSW/SH` 用 `AO00.PAL` @DAC64，按非 0 包围盒裁剪。
7. **特效**：`ICE/LIGHTN/BURN` 等，对应 16 色 PAL @DAC32。

关键脚本：`scripts/1846_shk3_finalunpack.py`（解包）、`1852_shk3_batch_final.py`（敌人/特效/武器批量）、`1854_shk3_enblk_batch.py`（敌人 BLK）、`1863/1865_shk3_blkman*.py`（角色精灵）。

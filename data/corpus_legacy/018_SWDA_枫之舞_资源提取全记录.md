## 0. 核心突破：MAP地图的4x4瓦片

### 0.1 问题的由来

MAP.LSK 解压后得到820个 `.dec` 文件，其中：
- 116个是调色板（1842字节）
- 96个是地图（magic=4，16bpp：低字节=tile_id，高字节=属性）
- 其余是瓦片集（大文件）

最初假设瓦片是 **8x8=64字节**，渲染后"轮廓对但细节没法看"——建筑模糊、地形像噪点。

### 0.2 关键直觉："如果瓦片是4x4呢？"

用户提出假设：瓦片可能是4x4而非8x8。验证结果：

| 瓦片尺寸 | 单瓦片字节 | 0001-0004合并后瓦片数 | 0012城镇效果 |
|----------|-----------|----------------------|-------------|
| 8x8 | 64 | 1600 | 建筑模糊，像噪点 |
| **4x4** | **16** | **6400** | **城墙、城门、房屋、人物全部清晰** |

**4x4瓦片渲染的0012城镇地图**：

![0012城镇地图](../extracted/SWDA_枫之舞/map_rendered/map_0012.png)

可以清晰辨认：城墙、城门、道路、多栋中式建筑、草地、水域、树木、人物。

**4x4瓦片渲染的0005野外地图**：

![0005野外地图](../extracted/SWDA_枫之舞/map_rendered/map_0005.png)

河流、山脉、森林、桥梁、建筑、道路全部清晰。之前8x8时的"青色噪点"实际是河流。

### 0.3 为什么8x8会错？

8x8假设下，每个瓦片被放大了4倍（面积）。原本4x4的精细像素被当作8x8渲染，导致：
- 建筑细节被拉伸模糊
- 河流像素块被放大成"噪点"
- 地形过渡不自然

4x4才是DOS游戏的标准瓦片尺寸（VGA 320x200下，4x4瓦片=80x50瓦片满屏）。

## 1. MAP地图格式规范

### 1.1 文件组织

MAP.LSK 解压后，文件按**动态分组**组织，不是固定7个一组：

```
[调色板] [瓦片集1] [瓦片集2] [瓦片集3] [瓦片集4] [地图] [对象数据]
   ↑                                                ↑
 1842字节                                   magic=0x0004
```

- **调色板**：1842字节，`pal_data[2:2+768]` 是768字节VGA 6bit调色板
- **瓦片集**：调色板和地图之间的所有大文件（>1000字节），按文件名顺序合并
- **地图**：magic=u16(4)，16bpp像素数据
- **对象数据**：地图后面的小文件（怪物/NPC/事件数据，未解析）

### 1.2 调色板格式

```c
// 调色板文件（1842字节）
u16 unknown;        // 偏移0，可能是瓦片数量或标志
u8  palette[768];   // 偏移2，256色 × 3字节(R,G,B)
u8  padding[1072];  // 偏移770，剩余数据

// VGA 6bit → 8bit转换
r = palette[i*3 + 0] * 4;
g = palette[i*3 + 1] * 4;
b = palette[i*3 + 2] * 4;
```

### 1.3 地图文件格式

```c
// 地图文件（magic=0x0004）
u16 magic;      // 偏移0，固定为4
u16 pal_off;    // 偏移2，像素数据结束位置（=8 + w*h*2）
u16 height;     // 偏移4，地图高度（瓦片数）
u16 width;      // 偏移6，地图宽度（瓦片数）
u16 tiles[w*h]; // 偏移8，16bpp瓦片数据
                 //   低字节 = tile_id (0-255)
                 //   高字节 = 属性 (bank/翻转/层级)
```

### 1.4 属性字节位定义

```
高字节 (8 bits):
┌───┬───┬───┬───┬───┬───┬───┬───┐
│ 7 │ 6 │ 5 │ 4 │ 3 │ 2 │ 1 │ 0 │
└───┴───┴───┴───┴───┴───┴───┴───┘
  │   │   │   │   │   └───┴───┴───┘
  │   │   │   │   │        └── bank (0-7)
  │   │   │   │   └──────────── 未使用 (0%)
  │   │   │   └──────────────── vflip (垂直翻转, 0.5%)
  │   │   └──────────────────── 未使用 (0%)
  │   └──────────────────────── hflip (水平翻转, 3%)
  └──────────────────────────── is_top (顶层对象, 11%)
```

- **bank**：选择瓦片集的bank，`global_id = bank * 256 + tile_id`
- **hflip**：水平翻转瓦片（位6）
- **vflip**：垂直翻转瓦片（位4）
- **is_top**：顶层对象（位7），渲染时覆盖在底层之上

### 1.5 瓦片寻址与渲染

```python
# 瓦片集合并：调色板和地图之间的所有大文件按顺序合并
all_tiles = b''
for ts_file in tileset_files:
    data = ts_file.read_bytes()
    rem = len(data) % 16  # 4x4=16字节
    if rem != 0:
        data = data[:-rem]  # 去掉末尾余数
    all_tiles += data

# 瓦片寻址
global_id = (high & 7) * 256 + tile_id
offset = global_id * 16  # 4x4=16字节

# 渲染（支持翻转）
for dy in range(4):
    sy = 3-dy if vflip else dy
    for dx in range(4):
        sx = 3-dx if hflip else dx
        pidx = all_tiles[offset + sy*4 + sx]
        color = palette[pidx]
```

### 1.6 底层+顶层合成渲染

```python
# 两遍渲染：先画底层，再画顶层覆盖
bottom = Image.new('RGB', (w*4, h*4))
top = Image.new('RGBA', (w*4, h*4), (0,0,0,0))

for each tile:
    if is_top:
        draw on top (RGBA, alpha=255)
    else:
        draw on bottom (RGB)

composite = bottom.convert('RGBA')
composite.alpha_composite(top)
result = composite.convert('RGB')
```

顶层对象包括：建筑、树木、人物、桥梁等需要覆盖在地形之上的元素。

## 2. LSK文件格式（CD/DO/SA）

### 2.1 LSK归档结构

LSK是大宇自定义归档格式，包含多个子文件。解压后：
- `CD/`：CD动画帧（全屏背景）
- `DO/`：角色行走图（多方向）
- `SA/`：战斗动画/特效
- `MAP/`：地图数据（调色板+瓦片集+地图）

### 2.2 解压算法：unicorn模拟RPGViewer

LSK子文件使用大宇自定义压缩，无法用标准LZSS解压。通过unicorn模拟RPGViewer的解压函数：

```
函数地址: 0x4ee390 (layer1解压)
调用约定: ecx=输入数据, edx=输入长度, 栈=输出缓冲区/usize/1
关键坑: PE段用vsize映射（不是raw size），IAT修复，全局变量重置
```

### 2.3 DO/SA透明PNG转换

DO/SA的调色板索引254是绿色背景 `RGB(0,156,88)`，需要转为透明：

```python
# DO调色板位置: lsk/DO/0038.bin 偏移2处，768字节VGA 6bit
pal_data = (DO_DIR / '0038.bin').read_bytes()
pal = pal_data[2:2+768]

# 转换为RGBA PNG，索引254设为透明
for each pixel:
    if pidx == 254:
        rgba = (0, 0, 0, 0)  # 透明
    else:
        rgba = (r, g, b, 255)
```

## 3. RSK文件格式（DOR/MENU/MEO）

### 3.1 两层压缩结构

RSK文件使用**两层压缩**：
1. **Layer1**（0x4ee390）：deflate风格动态Huffman + LZSS，解压所有帧数据
2. **Layer2**（0x447f40）：RLE变体，部分帧需要二次解压

Layer2的帧数据前2字节是签名：
- `4e 54` (0x544e='NT')：Normal Tile，RLE压缩
- `4d 54` (0x544d='MT')：Modified Tile，RLE变体
- 其他：原始像素数据

### 3.2 关键修复：DOR/MENU全黑问题

**最初错误**：用`find_palette()`从数据末尾搜索内嵌调色板，但DOR/MENU没有内嵌调色板，导致全黑。

**修复**：使用DO调色板（`0038.bin@2`），768字节VGA 6bit。

### 3.3 MENU layer2修复

**最初错误**：MENU偏移表格式的帧直接当原始像素，导致部分帧（079/085/086/087/165/166/176/178/179）变成噪点。

**修复**：MENU偏移表帧也可能是layer2压缩，需要判断像素头`4e54`/`4d54`，如果是则走layer2解压。

修复后：
- MENU_079 = 棕色按钮条
- MENU_165/166 = 地图片段
- MENU_176 = 绿色对话气泡
- MENU_179 = 绿色边框对话框

**MENU_176绿色对话气泡**：

![MENU_176](../extracted/SWDA_枫之舞/rsk_png/MENU_176.png)

### 3.4 RSK多帧格式

| 格式类型 | 文件 | 帧索引方式 |
|----------|------|-----------|
| 索引表 | DOR1/DOR3 | `[u16 idx_size][u16 offsets[]]` |
| 偏移表 | MENU/MEO | `@0开始u16帧偏移数组` |
| 单帧 | DOR2/DOR4 | 直接是一帧数据 |

注意：帧数据可乱序存储（DOR3关键发现），必须按偏移表读取，不能按顺序。

## 4. 经验教训

### 4.1 瓦片尺寸：不要假设8x8

**错误**：看到地图数据就假设瓦片是8x8（很多游戏的标准）。
**教训**：DOS游戏在320x200分辨率下，4x4瓦片更常见（80x50瓦片满屏）。验证方法：用不同尺寸渲染，看哪个尺寸下建筑/地形细节清晰。

### 4.2 调色板：不要假设内嵌

**错误**：从RSK数据末尾搜索内嵌调色板。
**教训**：大宇游戏的调色板通常是独立文件（DO的0038.bin），不是内嵌在图像数据里。

### 4.3 压缩：不要假设标准算法

**错误**：尝试480+种LZSS参数组合，全部失败。
**教训**：大宇使用自定义压缩（deflate风格Huffman + LZSS混合），标准算法无法解压。正确路径是反汇编定位解压函数，用unicorn模拟执行。

### 4.4 unicorn模拟的关键坑

1. **PE段用vsize映射**，不是raw size（否则BSS段缺失，全局变量错误）
2. **IAT修复**：导入函数需要stub
3. **全局变量重置**：每次调用前重置全局状态
4. **调用约定**：ecx=输入，edx=长度，栈传输出缓冲区

### 4.5 动态分组：不要假设固定结构

**错误**：假设MAP文件是固定7个一组（pal+4ts+map+obj）。
**教训**：实际是动态分组——每个地图找前面最近的调色板，中间的大文件都是瓦片集。不同地图组的瓦片集数量和大小不同。

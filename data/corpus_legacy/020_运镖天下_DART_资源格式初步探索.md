## 4. 部分分析格式

### 4.1 L.PAK / R.PAK — 立体图形归档 ✅

**重大突破**：L.DIC/R.DIC是PAK的**文件分配表**，PAK包含643个子文件，是**立体图像对**（L=左眼，R=右眼）。

#### 4.1.1 DIC文件分配表格式

**L.DIC / R.DIC**（5144字节）：
```
每条记录8字节，共643条（5144 / 8 = 643）
偏移  大小  说明
0     4     u32 offset — 子文件在PAK中的偏移
4     4     tag — "L.P\0" (0x0050004c)，文件类型标识
```

**偏移序列示例**：`0, 1226, 2697, 4167, 5543, 5784, 6025, 6266, 6507, 7733, ...`

子文件大小 = 下一条偏移 - 当前偏移。

#### 4.1.2 子文件格式（行结构图像）

**头部**：可变长度的`08 4c 00`重复填充（通常6字节，部分文件24字节）

**隐藏行（第一行）**：文件头后紧跟简化行标记`00 XX 04 YY`（4字节）+ 像素数据
- XX = 行左偏移
- YY = 参数
- 像素数据到第一个完整行标记结束

**行结构**：后续每行9字节头 + 原始像素数据
```
偏移  大小  说明
0     6     行标记：00 00 08 00 00 00
6     1     xx — 行左偏移（X起始位置）
7     1     固定：04
8     1     yy — 参数（无0值时=行宽；有0值时=首零偏移）
9     N     原始8bpp像素数据（到下一行标记或文件结束）
```

**行特征**：
- xx值从大到小再到大，形成圆形左右边界
- 像素数据是连续的8bpp颜色索引，**无RLE压缩**
- **颜色索引0 = 透明/黑色背景**（不是RLE转义符！）
- **图像方向：不翻转，行0在顶部**（DOS游戏图像从上到下存储）
- 颜色渐变：3f→3e→3d→3c→3b→3a... 形成球体光照效果
- 典型图像：75+1行（含隐藏行），最大宽度约64像素

**图像方向确认**：
- 不翻转（行0在顶部）：金/棕色在顶部（头部/头盔），蓝/绿色在底部（身体/衣服），符合角色方向
- 翻转后：蓝/绿色在顶部，金/棕色在底部，方向错误
- **正确方向：不翻转**（与游戏截图中的角色方向一致）

**调色板优化（v7）**：
- 从游戏截图提取145种唯一颜色（确认8bpp模式）
- 通过SGHERO PAL1索引映射到截图颜色，得到更精确的调色板
- v7版本颜色最接近游戏实际画面
- 映射方法：对SGHERO PAL1的每个索引，在截图颜色中找欧氏距离最近的颜色

**行内X,4,Y模式结论**：
- 出现在行49-66（图像下半部分）
- 经多种假设验证（子段标记、跳过标记、RLE），均导致图像拉宽或变形
- **结论：X,4,Y是普通颜色索引，4就是颜色4（深红色），不是特殊标记**
- 行结构是简单的连续8bpp像素，无RLE压缩或子段

**文件头填充长度可变**：
- 0451: 6字节（2次`08 4c 00`）
- 0032: 36字节（12次`08 4c 00`）
- 0200: 30字节（10次`08 4c 00`）
- 解析时需跳过所有连续的`08 4c 00`，再找隐藏行标记

**RLE证伪（关键教训）**：
- 行6像素：`[63,63,63,63,63,62,0,2,4,48,62,...]`，初看`0,2,4`像RLE标记
- 但行11：`[...,0,6,4,43,0,174,174,11,11,11,...]`，若0是转义符则count=174不合理
- 行17：`[0,35,45,43,43,...]`，0就是颜色0（透明）
- 按`0,count,color`RLE解压会产生640x75水平条纹，证明假设错误
- **最终结论：0是颜色索引0（透明），像素数据无压缩，渲染时颜色0应设为透明**

**图像方向发现与纠正**：
- 原始渲染（行0在顶部）：金/棕色在顶部，蓝/绿色在底部
- 最初误认为"上下翻转后更像角色"（蓝/绿在顶部=头盔，金/棕在底部=身体），生成了v5翻转版
- **用户反馈"上下反了"后，用游戏截图对比验证**：截图中角色头部在顶部、身体在底部，与不翻转版本一致
- **最终结论：不翻转，行0在顶部**（v5翻转版方向错误，已废弃）
- 教训：方向判断必须以游戏实际画面为准，不能凭"看起来像"猜测

**子文件大小分布**：

| 241 B | 216 | 空帧/填充帧（全`08 4c 00`重复） |
| 1226 B | 7 | 小图像 |
| 1247 B | 9 | 小图像 |
| 其他 | ~400 | 各种尺寸图像 |

#### 4.1.5 调色板（详细调查）

**问题**：DART没有独立调色板文件（SGHERO有PAL0/PAL1=768字节）。PAK图像是8bpp索引色，必须有调色板才能正确渲染。

**调查过程**：

1. **简化VGA调色板**（失败）：最初用标准16色+灰度渐变的简化调色板渲染，颜色完全错误（绿/蓝/紫/粉噪点）。

2. **借用同引擎SGHERO调色板**（部分成功）：
   - SGHERO PAL0：偏红/绿，效果差
   - **SGHERO PAL1**：金属质感金/棕/蓝渐变，效果大幅改善，可识别内容（宝珠、角色、物品）
   - 但用户反馈"颜色有问题"，对比游戏实际截图（蓝棕/暖色调），SGHERO PAL1偏蓝绿/金属色

3. **在DART0.EXE中搜索调色板**（未找到）：
   - 搜索6bit VGA调色板（768字节，所有值<=63）：找到的候选全是全0区域或灰度渐变表（@0x4187c，非零色主要是R=G=B的灰度），不是主调色板
   - 搜索8bit调色板：0结果
   - 搜索调色板块格式（u16计数+u16索引/颜色数+RGB）：找到的候选数据不合理

4. **从游戏截图提取调色板**（不够精确）：
   - 用户提供两张游戏实际截图（人物选择界面、大地图界面）
   - 用PIL `quantize(colors=256)` 量化颜色
   - 裁剪全画面：调色板被Windows窗口白色/UI金色主导，渲染偏黄/金
   - 裁剪地图中心区域：提取到游戏主要颜色（深蓝(0,93,125)、棕色(109,65,52)、金棕(190,134,60)等），渲染效果偏暖但仍不够精确
   - 原因：截图是缩放后的，颜色有插值；且无法精确还原6bit VGA调色板

5. **反汇编VGA调色板设置代码**（定位缓冲区）：
   - 找到`mov dx, 0x3c8`（8处）和`mov dx, 0x3c9`（2处）
   - **@0x1f610**：简单调色板设置函数，从`esi`读取768字节输出到0x3c8/0x3c9
   - **@0x1ff71**：16位打包格式调色板设置（`lodsw` + `shr 2`提取6bit值）
   - **@0x204f6 / @0x2054a**：调色板动画/淡入淡出，从**0x3223b**缓冲区输出
   - **@0x1f631**：从0x3c7/0x3c9读取当前调色板到0x3223b
   - 调色板缓冲区在内存**0x3223b**（低内存，可能由DOS/TSR加载）
   - 未找到直接调用调色板函数的指令（可能通过寄存器间接调用或重定位修正）
   - 未找到直接引用0x3223b的指令

**结论**：
- DART的精确调色板**不在EXE中**，很可能内嵌在**JMC加密归档**中
- 调色板在运行时被加载到内存0x3223b，然后通过VGA端口设置
- **SGHERO PAL1是基础方案**，可识别图像内容，色调偏蓝绿
- **暖色调调整版（推荐）**：在SGHERO PAL1基础上增加红/绿通道、减少蓝通道，更接近游戏实际的蓝棕/暖色调
- 精确调色板需破解JMC后才能获取，或通过DOSBox调试读取0x3223b（用户禁止DOSBox调试）

**暖色调调色板调整公式**（在SGHERO PAL1 8bit值基础上）：
```
R' = min(255, R * 1.2 + 10)
G' = min(255, G * 1.1 + 5)
B' = max(0, B * 0.85)
```

**KMeans调色板尝试**（未采用）：
- 从游戏截图用KMeans量化256色，颜色值接近游戏实际
- 但KMeans按聚类顺序排列，与游戏原始调色板索引不匹配，渲染颜色杂乱
- 用标题画面（绿色竹林）和战斗场景（棕色洞穴）两张新截图分别提取，效果均差
- SGHERO索引+KMeans最近色映射：部分改善但仍有噪点
- 结论：保持SGHERO PAL1索引顺序最重要，颜色值可微调

### 4.2 LEVEL_A-P — 关卡配置

**结构**：
- 固定 97,957 字节
- 前30字节全0
- @0x1e 开始为u16数组：
  ```
  [0]=1, [1]=65535, [2]=65535, [3]=3000, [4]=5000, [5]=8000,
  [6]=12000, [7]=17000, [8]=65535, [9]=1, [10]=1, [11]=1, ...
  ```
- 3000/5000/8000/12000/17000 为递增序列（可能是镖车价格/经验值表）
- 65535(0xffff) 为分隔/结束标记
- SAVE_0-4存档同大小，推测存档=关卡数据+玩家状态

### 4.3 RPG.SCN + RPG.15 — 脚本

- RPG.SCN：u16递增数组 [0,2,3,4,5,6,7,8,10,11,13...]，脚本偏移表
- RPG.15：脚本数据（开头大量0）
- 与SGHERO的RPG.SCN/RPG.15完全对应

## 5. 未破解格式

### 5.1 JMC + HED — 加密资源归档（核心难点）

**与SGHERO同引擎**：DART的JMC/HED文件结构与三国雄霸天下(SGHERO)完全一致。

**SGHERO的研究结论**（参考 `docs/013_三国雄霸天下_SGHERO_资源格式逆向与素材提取.md`）：
- JMC不是压缩归档，而是**加密的字节码脚本格式**
- 结构：70字节头部 + 第一块（字节码脚本，加密）+ 后续数据块（资源数据，加密）
- 字节码命令集已识别（0xf8设置当前字节、0xfc场景切换、0xf0位置、0xa0绘制角色等）
- **解密方法未找到**：PLAY.EXE加载时直接读文件到内存，无解密步骤
- 推测解密发生在DOS中断钩子/TSR/程序启动时全局解密
- 已证伪：单/双字节XOR、ADD/SUB、zlib、位置XOR、ARJ

**DART的差异**：
- DART0.EXE是LE格式32位程序（SGHERO是16位MZ），引擎版本可能不同
- TEST.JMC=3.4MB（SGHERO最大861KB），数据量更大
- DART有L.DIC/R.DIC字典文件（SGHERO只有TEST.DIC=186B），可能用于解压

**已证伪的方法**（继承SGHERO结论）：
- 单字节XOR（0-255）
- 双字节XOR（65536种）
- ADD/SUB
- zlib（wbits 15/-15/31/47）
- 位置XOR

### 5.2 调色板（已调查，临时方案）

**DART没有独立的调色板文件**（SGHERO有PAL0/PAL1=768字节）。

**调查结论**（详见4.1.5节）：
- EXE中无标准768字节6bit VGA调色板
- 调色板缓冲区在运行时内存0x3223b，数据来源未知（推测在JMC中）
- 反汇编已定位调色板设置函数@0x1f610/@0x1ff71/@0x204f6
- **当前方案**：借用同引擎SGHERO的PAL1调色板，可识别图像内容，色调偏蓝绿
- **精确调色板**：需破解JMC后获取，或通过DOSBox调试读取0x3223b（用户禁止）

## 9. 反汇编DART0.EXE的发现

### 9.1 LE格式解析

DART0.EXE是Watcom C/C++ 32位编译的LE格式可执行文件：
- 2个对象：代码段（R+X+PRE，vsize=0x1da03，30页）+ 数据段（BSS）
- 代码段文件偏移@0x14050，VA基址0x10000
- 入口点：对象1:0x11a38

### 9.2 资源字符串

代码段中存储了连续的字符串表@文件0x30f10：
```
h.dic\0total.man\0l.pak\0l.dic\0r.pak\0r.dic\0
```

但反汇编中**未找到直接引用这些字符串的指令**，可能通过字符串表基址+偏移间接访问，或运行时构造文件名。

### 9.3 文件操作函数

- @0x10a03：打开4个文件（文件名指针0x1924/0x192a/0x1930/0x1936，疑似dart0-3.buh）
- @0x1c8c7：打开文件读26字节头（文件名运行时构造@0x306bb）
- @0x1f284：打开文件写（错误日志？）

### 9.4 VGA调色板设置代码

通过搜索`mov dx, 0x3c8`（调色板索引端口）和`mov dx, 0x3c9`（调色板数据端口），定位到多个调色板设置函数：

**@0x1f610 — 简单768字节调色板设置**：
```asm
mov dx, 0x3c8      ; 调色板索引端口
xor al, al         ; 起始索引0
out dx, al         ; 设置索引
inc dx             ; dx = 0x3c9（数据端口）
mov ecx, 0x300     ; 768字节 = 256色 × 3通道
rep outsb dx, [esi] ; 从esi输出768字节
ret
```
调用者需设置`esi`指向调色板数据。

**@0x1ff71 — 16位打包格式调色板设置**：
```asm
mov dx, 0x3c8
xor al, al
out dx, al
inc dx             ; 0x3c9
inc si
mov cx, 0x180      ; 384次循环
lodsw ax, [esi]    ; 读取16位（打包两个6bit值）
shr al, 2          ; al>>2 = 6bit R
out dx, al
mov al, ah
shr al, 2          ; ah>>2 = 6bit G
out dx, al
loop               ; 循环
```
从16位打包数据中提取6bit调色板值。

**@0x204f6 / @0x2054a — 调色板动画/淡入淡出**：
```asm
mov dx, 0x3c8
xor al, al
out dx, al
inc dx
mov esi, 0x3223b   ; 调色板缓冲区地址
mov ecx, 0x300
rep outsb dx, [esi] ; 从0x3223b输出768字节
```
调色板缓冲区在内存**0x3223b**（低内存）。

**@0x1f631 — 读取当前调色板**：
```asm
mov edi, 0x3223b   ; 调色板缓冲区
mov dx, 0x3c7      ; 读索引端口
xor al, al
out dx, al
mov dx, 0x3c9      ; 读数据端口
mov ecx, 0x300
rep insb [edi], dx ; 读取768字节到0x3223b
```

**关键发现**：
- 调色板缓冲区地址0x3223b是低内存地址（<1MB），可能由DOS/TSR加载
- 未找到直接调用调色板函数的指令（可能通过寄存器间接调用）
- 未找到直接引用0x3223b的指令
- 调色板数据很可能在JMC加密归档中，运行时解密后加载到0x3223b

### 9.5 反汇编的局限

Watcom C优化程度高，函数边界不明显，字符串引用方式复杂。对于PAK格式，**直接分析DIC文件比反汇编更高效**。

## 10. 经验总结

1. **DIC是关键**：L.DIC/R.DIC的名字容易被误认为"字典/解压表"，实际是**文件分配表**。每条8字节（u32偏移 + "L.P\0"标签），直接索引PAK中的子文件。破解归档格式时，同名的小文件（DIC/HED/IDX）应优先检查是否是索引表。

2. **行结构图像**：子文件不是传统的连续像素，而是**每行带左偏移的行结构**。`00 00 08 00 00 00 XX 04 YY`是行标记，XX是左偏移。这种格式适合存储圆形/球体等非矩形图像，通过左偏移形成轮廓。

3. **立体图像对**：L/R命名不是左右声道，而是**左右眼立体图像**。两个PAK大小完全相同，子文件偏移一致，但内容有视差。这是DOS时代罕见的立体3D游戏技术。

4. **同引擎识别**：通过文件结构（JMC+HED+DIC+RPG.15/SCN）识别出DART与SGHERO同引擎，避免重复劳动，直接继承SGHERO的研究结论（JMC是加密字节码、已证伪的解密方法等）。

5. **PAK不是音频**：最初根据L/R命名和41.5%相似度推测为立体声音频，实际验证排除（平均值≠128、无VOC签名、唯一值仅84种）。正确做法是先检查数据特征再下结论。

6. **反汇编不是万能的**：对于有索引表的归档格式，直接解析索引表比反汇编EXE更高效。反汇编适合破解无索引的加密格式（如JMC）。

7. **VOC提取最简单**：有标准文件头+偏移表的格式最容易提取，应优先处理。

8. **调色板调查方法论**：对于无独立调色板文件的游戏，应按以下顺序调查：(1)借用同引擎游戏的调色板；(2)在EXE中搜索6bit/8bit 768字节调色板块；(3)反汇编VGA端口访问（0x3c8/0x3c9）定位调色板设置函数和缓冲区；(4)**从游戏截图提取颜色并通过同引擎索引映射**（DART v7的成功方案）。DART的案例证明，同引擎调色板+截图颜色映射可以得到非常接近实际画面的效果。

9. **反汇编定位VGA调色板**：搜索`mov dx, 0x3c8`/`mov dx, 0x3c9`/`out dx, al`是定位调色板设置代码的有效方法。调色板缓冲区地址（如0x3223b）可以通过`mov esi, addr` + `rep outsb`模式识别。

10. **方向判断必须以实际画面为准**：最初凭"看起来像"猜测需要上下翻转（v5），用户反馈"上下反了"后用游戏截图对比才确认不翻转才是正确方向。教训：图像方向、颜色等视觉判断必须有游戏实际画面作为验证基准，不能凭感觉猜测。

11. **X,4,Y模式的证伪方法**：当数据中出现疑似特殊标记时，应提出多种假设并逐一验证。DART中行49-66的`X,4,Y`模式，先后验证了子段标记、跳过标记、RLE三种假设，均导致图像拉宽/变形，最终确认是普通颜色索引（4=深红色）。证伪过程比猜测更有价值。

12. **截图调色板映射的关键**：从截图提取颜色后，不能直接按KMeans聚类顺序作为调色板（索引不匹配会导致颜色杂乱）。正确方法是**保持同引擎调色板的索引顺序**，将每个索引的颜色替换为截图中最接近的颜色。这样既保留了正确的索引映射，又获得了精确的颜色值。

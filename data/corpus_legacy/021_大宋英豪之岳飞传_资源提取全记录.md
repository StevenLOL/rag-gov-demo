### 压缩方式

BMHD中压缩字段=1，表示**PackBits压缩**：

```python
def decode_packbits(data, max_pixels):
    out = []
    p = 0
    while p < len(data) and len(out) < max_pixels:
        n = data[p]
        p += 1
        if n < 128:          # 原始数据
            count = n + 1
            out.extend(data[p:p+count])
            p += count
        elif n > 128:        # RLE
            count = 257 - n
            out.extend([data[p]] * count)
            p += 1
    return out
```

### 图像压缩：PCX风格RLE

图像数据使用**PCX风格RLE**（高2位标记法）：

```python
def decode_pcx_rle(data, max_pixels):
    out = []
    p = 0
    while p < len(data) and len(out) < max_pixels:
        b = data[p]
        if (b & 0xc0) == 0xc0:   # 高2位=11，RLE
            count = b & 0x3f     # 低6位=重复次数
            p += 1
            out.extend([data[p]] * count)
            p += 1
        else:                     # 直接输出
            out.append(b)
            p += 1
    return out
```

### 营帐左右半拼接（关键发现）

DATA.GRP索引500-529是营帐类瓦片（t19=128），**成对出现**：

### 每行单元数(upr)的确定——直角网格条纹分析法

L1有3640个9字节单元，正确的upr（每行单元数）不能从头部直接读取，需通过**直角网格条纹分析**确定：

1. 将单元数据按候选upr排列成直角网格
2. 用瓦片值低字节着色
3. **错误的upr会产生明显的斜向或垂直条纹**（因为行边界切错了数据）
4. **正确的upr网格最随机、无规则条纹**

L1的候选upr对比结果：
- upr=40：明显斜向条纹（从左上到右下，周期5行）❌
- upr=52：垂直条纹 ❌
- upr=56：**最随机，无条纹** ✅
- upr=65：垂直条纹 ❌
- upr=91：垂直条纹 ❌

**结论：L1的upr=56，rows=65，stride=112**（3640/56=65，整除）。

条纹周期推算：upr=40时每5行重复一次，对应偏移量16，即正确upr=40+16=56。

### 渲染规则（反编译确认）

1. **奇偶行交错**：偶数行逻辑列=0,2,4...，奇数行逻辑列=1,3,5...
2. **数据索引**：`idx = (col + stride*row) >> 1`（不是row*upr+unit！）
3. **等距坐标**：`iso_x = (col-row)*36`，`iso_y = (col+row)*18`
4. **大瓦片底部中心锚点**：`paste_x = iso_x - tw/2`，`paste_y = iso_y + 18 - th`
5. **背景色**：普通地图绿色草地RGB(40,100,12)，L26世界地图蓝色水域RGB(0,0,168)
6. **透明处理**：调色板索引0设为透明

**压缩算法（IDA Pro反编译确认）**：

**Type 1** (`sub_223D0`, PCX风格RLE)：
```c
do {
    b = get_byte();
    if ((b & 0xC0) == 0xC0) {  // >=192
        count = b & 0x3F;       // 低6位=重复次数
        color = get_byte();     // 总是读颜色(即使count=0!)
        if (count > 0) repeat(count, color);
    } else {
        copy(b);
    }
} while (bytes_written < row_size);
```
**注意**：即使count=0（b=0xC0），也要读一个颜色字节，否则数据错位产生横纹！这是早期提取出现横纹的根本原因。

**Type 2** (`sub_28A10`, 变体RLE)：
```c
do {
    b = get_byte();
    if (b < 128) {
        count = b + 1;          // 直接复制b+1个字节
        copy_raw(count);
    } else if (b > 128) {
        count = 257 - b;        // 重复257-b次下一字节
        color = get_byte();
        repeat(count, color);
    }
    // b==128: 跳过(特殊标记)
} while (bytes_written < row_size);
```

### DATA.GRP瓦片集（970个瓦片，35个索引集，反编译最终确认）

#### 为什么最后才发现瓦片分类？——三个错误假设的连锁反应

瓦片分类（草丛/树木/农田/建筑/岩石）直到破解的最后阶段才发现，根本原因是**三个错误假设层层叠加，导致早期始终只看到前48个棕色泥地地形瓦片**：

**错误1：v13/v14搞反，以为只有35个瓦片**
- DATA.GRP头部偏移5-6是v13=35，偏移7-8是v14=970
- 早期误以为v13=35是瓦片数，v14=970是索引表数
- 实际相反：**v13=35是索引集数，v14=970是瓦片数**
- 后果：只解析了35个条目，后面935个瓦片完全被忽略

**错误2：ptr当成数据区相对偏移，解压出垃圾数据**
- 20字节条目的ptr字段，早期以为是"数据区相对偏移"（ptr + 19677 = 文件偏移）
- 实际**ptr是文件绝对偏移**——条目0 ptr=0x4cdd=19677正好是数据区起始
- 后果：用相对偏移解压时，文件偏移 = 19677 + ptr = 19677 + 19677 = 39354，指向错误数据，解压出横纹/噪点，误以为后面的瓦片格式不同或已损坏

**错误3：实际高度用h而非f12，解压失败**
- 20字节条目的h字段（72,57,52等）是包围盒高度
- **实际像素行数是f12字段**（35,36,27等）
- 早期用h=72解压，需要72×72=5184像素，但RLE压缩数据只够36行，解压失败或产生横纹
- 后果：即使ptr正确，用错误高度也解压不出正确图像

**突破点**：IDA Pro反编译`sub_20970`（DATA.GRP加载函数），一次性纠正了以上三个错误。提取全部970个瓦片后，按35个索引集分组，才发现集1是草丛/树木、集6是农田、集7是建筑、集16是岩石——这些对象瓦片在早期的35个瓦片假设下根本不存在。

## 十、经验总结

### 基础格式经验

1. **调色板先确认**：DEFAULT.PAL是8bit直接用，不是6bit需×4。最大值252非255。

2. **LBM是IFF PBM不是ILBM**：FORM类型是`PBM `而非`ILBM`，压缩方式是PackBits。PIL无法直接识别，需手动解析IFF块。

3. **PIC压缩是PCX风格RLE**：高2位标记法（>=192时低6位是重复次数），count=0即0xC0也必须读颜色字节否则横纹。

4. **PIC实际尺寸=f1×f3**：f2是画布高度不是实际高度。

5. **MAP宽高是大端**：与PIC的小端不同，字节序要逐个格式验证。

6. **归档格式多样化**：同游戏内有LIB\x01（PIC/MENU/MOUSE）、LIB\x00（MAN/MAGIC）、GRP\x00（DATA）三种归档格式，不能假设统一。

### 反编译方法论

7. **IDA反编译是DOS游戏格式破解的终极手段**：MAN.LIB、DATA.GRP、MAP的正确格式都是通过IDA Pro 7.6反编译YFZ.EXE（DOS4GW LE格式32位保护模式）确认的。早期所有猜测（48字节条目、35个瓦片、相对偏移、行数=h、8bit地形层）全部错误。

8. **ptr字段必须验证是绝对偏移还是相对偏移**：DATA.GRP的ptr是文件绝对偏移（条目0 ptr=0x4cdd=19677正好是数据区起始）。验证方法：条目0的ptr+size应等于条目1的ptr。

9. **h字段不一定是实际高度**：DATA.GRP的h是包围盒高度，f12才是实际像素行数。MAN.LIB的h也不是行数，di才是。

### 透明处理经验

10. **不要把所有黑色都变透明**：早期将所有RGB(0,0,0)设为透明，导致角色黑色头发、眼睛、衣服消失。正确做法：只将**调色板索引0**设为透明，保留索引23等其他黑色。必须在P模式下根据原始索引值设置alpha。

### MAP格式破解经验

11. **MAP单元可能含多层信息**：9字节单元不是单一瓦片索引，而是四角地形（4字节）+主对象（2字节）+主导地形（1字节）+动态对象（2字节）的三层结构。分析未知字段时要检查值分布是否与已知字段相关。

12. **大对象可能分左右半存储**：营帐瓦片500-529成对出现（偶数=左半，奇数=右半），单独渲染右半会导致"营帐只有一半"。发现对象不完整时要检查是否有配套的另一半瓦片。

13. **直角网格条纹分析法确定行列数**：当地图头部没有明确的行列数时，将数据按候选upr排列成直角网格，错误的upr会产生明显的斜向/垂直条纹，正确的upr网格最随机。这是确定等距地图行列数的可靠方法。

14. **v4-1可能是运行时对象表索引，不是文件直接索引**：MAP瓦片值超出DATA.GRP范围（如12288）时，不是数据错误，而是引用了运行时对象表中MAN.LIB精灵等其他资源。

15. **低8位恰好能渲染出"看起来合理"的结果会延误纠错**：MAP的b4低8位都是0-52的棕色泥地值，渲染出绿色背景+棕色道路，虽然缺少树木建筑但"看起来像地图"。必须用用户反馈（"要有树林帐篷"）驱动深入分析，不能满足于"看起来合理"。

### 通用方法论

16. **瓦片分类要提取全部瓦片才能发现**：早期只看前48个地形瓦片，以为DATA.GRP只有泥地。提取全部970个后才发现集1=草丛树木、集6=农田、集7=建筑、集16=岩石、集18=人物精灵。

17. **GameExtractor方法论**：先看文件签名→头部结构→条目表→数据压缩→验证渲染。每一步都要有字节级证据，不猜。用户反复指出错误时，回到反编译代码逐行重读，不要在错误假设上继续修补。

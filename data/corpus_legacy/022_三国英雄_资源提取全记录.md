XMI（Miles Sound System MIDI）格式结构：
```
FORM/XDIR/INFO + CAT /FORM/XMID/TIMB(音色表) + EVNT(MIDI事件)
```

- `TIMB` 块：音色映射表
- `EVNT` 块：标准 MIDI 事件流（带运行状态）
- 转换方式：提取 EVNT 块，包装为 MThd+MTrk 标准 MIDI

**Bug记录**：早期搜索 `b"MIDI"` 标记全部失败，实际 MIDI 事件在 `EVNT` 块中。

## 四、GRP 格式破解（地图瓦片包）—— IDA 反编译确认版

| 4 | 4 | size | 瓦片压缩大小（小端u32） |
| 8 | 2 | w2 | **RLE行宽**（含行尾元数据/填充，小端u16） |

| 14 | 2 | u1 | 未知（通常=h） |

**⚠️ 右侧竖条纹根因**：
- w2=80是RLE解码的行宽，但**实际图像只有w=72列**
- x=72~79是**行尾元数据/填充**，不是图像像素
- tile0的x73-79固定为`[117,5,243,165,235,104,144]`（所有行相同）
- tile3的x73-79固定为`[0,162,128,0,0,0,0]`（所有行相同）
- 用w2=80渲染会把元数据当像素显示，形成右侧竖条纹

### MAP 格式破解（地图索引）

| 偏移 | 长度 | 字段 | 说明 |
|------|------|------|------|
| 0 | 4 | magic | "MAP2" |
| 4 | 2 | width | 地图宽度（**大端**u16） |
| 6 | 2 | height | 地图高度（**大端**u16） |

| 16 | N×2 | layer1 | 第一层索引（地面层），u16小端 |

**等距渲染**：
- 瓦片尺寸 80×36（等距菱形）
- 奇数行偏移半个瓦片宽度（40px）
- 画布尺寸 = width×80+40 × height×18+36

## 六、RLE 压缩算法（IDA 反编译确认版）

> **重要更正**：早期猜测的"0=标记length+color"算法是错误的，会导致横纹（RLE长度117溢出行宽80）。
> 正确算法通过 IDA Pro 反汇编 `sub_3FB09` 函数确认，**同时适用于 GRP 瓦片和 LIB 图像**（PCX RLE 变体）。

### 算法核心（来自反汇编）

```asm
; sub_3FB09 - 逐行RLE解码
mov al, [si]          ; 读取字节c
and eax, 0C0h         ; 取高2位
cmp eax, 0C0h         ; 高2位是否=11?
jnz direct_pixel      ; 不是→直接像素
; 是RLE标记
mov al, [si]
and eax, 3Fh          ; 低6位=长度(0-63)
mov color, [si+1]     ; 下一字节=颜色
repeat length times color
direct_pixel:
draw 1 pixel color=c
```

### Python 实现（线性解码，GRP/LIB通用）

```python
def decode_pcx_rle(data, start, width, height, max_bytes, palette):
    img = Image.new("RGBA", (width, height), (0,0,0,0))
    px = img.load()
    x, y = 0, 0
    i = start
    end = min(start + max_bytes, len(data))
    pixels = 0
    total = width * height
    while i < end and pixels < total:
        b = data[i]; i += 1
        if (b & 0xC0) == 0xC0:      # >=192 是RLE标记
            length = b & 0x3F       # 低6位=长度(0-63)
            color = data[i]; i += 1
            for _ in range(length):
                if pixels >= total: break
                if color != 0:
                    px[x, y] = palette[color] + (255,)
                x += 1
                if x >= width: x = 0; y += 1
                pixels += 1
        else:                        # <192 是直接像素
            if b != 0:
                px[x, y] = palette[b] + (255,)
            x += 1
            if x >= width: x = 0; y += 1
            pixels += 1
    return img
```

### 右侧竖条纹的统一修复方法

GRP瓦片和LIB图像都存在"RLE行宽 > 实际渲染宽度"的问题，行尾的元数据/填充列被当成像素显示，形成右侧竖条纹。

**竖条纹特征（改进版检测）**：
- 竖条纹列**不在最右列**，而是在内部列，右侧有若干透明列
- 竖条纹列 >95% 非透明，颜色 <=3 种（通常1种）
- 例如0406的x=76列：100%非透明，1种颜色(0,0,0)黑色，x=77-79全透明

**修复方法**：从右往左扫描，跳过透明列，遇到第一列非透明列时检查是否是竖条纹，如果是则裁剪掉该列及其右侧所有透明列，重复直到遇到正常图像内容列。

```python
def is_stripe_col(img, col, height):
    nontrans = sum(1 for y in range(height) if img.getpixel((col,y))[3]>0)
    colors = set(img.getpixel((col,y))[:3] for y in range(height) if img.getpixel((col,y))[3]>0)
    return nontrans > height * 0.95 and len(colors) <= 3

def crop_stripes(img, max_cols=15):
    cropped = 0
    for _ in range(max_cols):
        if img.width <= 1: break
        for col in range(img.width-1, -1, -1):
            nontrans = sum(1 for y in range(img.height) if img.getpixel((col,y))[3]>0)
            if nontrans == 0: continue  # 跳过透明列
            if is_stripe_col(img, col, img.height):
                img = img.crop((0, 0, col, img.height))  # 裁剪竖条纹列及右侧
                cropped += 1
                break
            else:
                return img, cropped  # 正常图像内容, 停止
    return img, cropped
```

## 七、调色板问题

使用游戏根目录 `DEFAULT.PAL`（768字节纯RGB，8位，最大值255）作为全局调色板。

**已知问题**：
- DEFAULT.PAL 是 UI/界面调色板，**不是地图场景调色板**
- tile0（主要地面）颜色索引分布：idx0(1877次黑), idx15(751次黑), idx117(36次绿), idx5(36次深棕)...
- idx15在DEFAULT.PAL中是黑色(0,0,0)，但实际应为草地颜色 → 游戏运行时**动态修改调色板**
- 用真实游戏截图（320×200）量化256色调色板渲染，可得到正确的绿色草地效果
- 场景调色板的精确来源待确认（可能在SAN.EXE数据段中非连续存储，或运行时从DEFAULT.PAL修改）

**临时方案**：用真实截图量化调色板渲染地图瓦片，颜色接近真实游戏画面。

## 九、逆向过程中的关键突破

1. **IDA反编译确认GRP格式**：通过IDA Pro 7.6反汇编SAN.EXE，找到sub_44928（GRP加载）、sub_3FDCD（条目处理）、sub_3FB09（RLE解码）三个关键函数，确认头部5字节+19字节条目表的正确结构
2. **RLE算法更正**：早期猜测的"0=标记"算法导致横纹（RLE长度117溢出行宽80）。IDA确认正确算法是"高2位=11（>=192）为RLE标记，低6位=长度"
3. **等距菱形瓦片**：瓦片尺寸80×36（不是80×72），u1=36, u2=18，呈等距菱形，四角透明
4. **MAP大端尺寸**：MAP宽度/高度为大端u16（小端会得到17920×17664的荒谬值），索引为低字节瓦片索引+高字节属性
5. **3层地图数据**：MAP文件包含3层索引（地面层/物体层/遮挡层），每层width×height×2字节
6. **调色板动态加载**：DEFAULT.PAL是UI调色板，游戏运行时动态修改场景调色板（idx15在DEFAULT.PAL中是黑色但实际为草地颜色）

## 十、已知问题与后续方向

### 已知问题
1. **场景调色板未定位**：DEFAULT.PAL不是地图调色板，用截图量化调色板可近似但非精确。游戏运行时动态加载场景调色板，精确来源待确认
2. **SOLDIER.LIB**：仅解析到1个大图，士兵动画帧可能在图内以网格排列，需进一步切割
3. **MAP多层含义**：3层索引数据的具体含义（地面/物体/遮挡）需结合OBJ文件确认
4. **部分LIB条目误匹配**：MOUSE.LIB/WINDOW.LIB 后续条目可能为数据偶然匹配

### 后续方向
1. 在IDA中查找VGA调色板端口（0x3C8/0x3C9）写入代码，定位场景调色板加载逻辑
2. 解析.OBJ文件，结合MAP多层数据渲染带物体的完整地图
3. 切割SOLDIER.LIB大图为独立士兵动画帧
4. 分析.HUM（人物数据）文件格式
5. 用真实截图调色板批量重新渲染所有地图

## 十一、经验总结

1. **反编译优先于猜测**：GRP格式猜测了十几种RLE变体（v1-v12）均不正确，IDA反编译一次确认。逆向未知格式应优先反编译可执行文件
2. **RLE变体多样**：三国英雄的GRP用"高2位标记法（>=192）"，与岳飞传/其他游戏不同。每个游戏的RLE都需要通过反编译或字节模式确认
3. **字节序陷阱**：MAP尺寸是大端u16，GRP条目是小端。同一游戏内不同文件可能使用不同字节序
4. **等距视角瓦片**：战棋游戏常用等距菱形瓦片（宽>高），不要假设正方形瓦片。u1=h/2是等距特征
5. **调色板动态化**：DOS游戏常有多个调色板，全局DEFAULT.PAL不一定适用于所有资源。颜色索引大量指向"黑色"时应怀疑调色板被运行时修改
6. **条目连续性验证**：正确的条目表应满足`offset[i]+size[i]==offset[i+1]`（除间隙外），这是验证解析正确性的关键
7. **PCX内嵌调色板优先**：自带调色板的图像格式不应强制使用外部调色板

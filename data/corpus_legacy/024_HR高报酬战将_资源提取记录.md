## 二、LZSS解压算法（IDA Pro确认）

通过IDA 7.6反编译MAIN.EXE（DOS4GW保护模式，539KB），定位到解压函数 `sub_3480E`。

### 算法参数
- 窗口大小: 1024字节 (0x400)
- 窗口起始: 0xC（环形缓冲区前12字节保留）
- 初始位置: bx = 0x3BE = 958
- 标志位: 从bit0到bit7依次测试（1=literal, 0=match）

### 关键发现：绝对索引而非回溯距离
```
match时:
  b1 = 低8位offset
  b2 = 高2位offset + 6位length
  offset = ((b2 >> 6) << 8) | b1    (10位绝对索引 0-1023)
  length = (b2 & 0x3F) + 3          (3-66字节)
  si = offset                         ; 直接设为绝对索引
  读 window[si + 0xC]                ; 不是 (current - offset - 1)!
```

**这是与标准LZSS最大的不同**：offset是环形缓冲区中的绝对索引，不是回溯距离。

### 压缩数据格式
```
偏移  大小  说明
0     4     解压后大小 (LE32)
4     ...   LZSS压缩流
```

### 清零范围
IDA中只清零 window[0xC..0x3CC]（960字节），window[0x3CD..0x40B]未初始化。实际运行时未初始化区域可能影响解压，但Python实现中全部初始化为0。

### 类型B：LZSS压缩图像（按type细分）

#### B1: type=0x80 → 8bpp彩色（高4位颜色+低4位亮度，最终确认）
```
条目格式: 4字节解压大小(LE32) + LZSS压缩流
解压后: 5字节头部(显示w=128 LE16, 显示h=160, type=0x80) + 10240字节8bpp数据
实际尺寸: 128x80 (3头像横向) 或 64x160 (1竖版头像)
8bpp像素 = 高4位(16色调色板索引) + 低4位(亮度0-15)
最终颜色 = 调色板基色 × 亮度/15
```

**核心发现：8bpp不是灰度，也不是256色调色板索引，而是"高4位颜色+低4位亮度"的复合格式！**

- 高4位: 16色调色板索引（使用ED0.RGB调色板）
- 低4位: 亮度级别（0=最暗/黑，15=最亮/白）
- 着色公式: `RGB = (base_r × bright/15, base_g × bright/15, base_b × bright/15)`
- 调色板ED0.RGB关键色: 索引7=红(衣服), 索引8=棕(头发), 索引12-14=肤色, 索引15=白
- **透明色: 白色(255,255,255)**，对应值255（索引15+亮度15）。**值0是黑色，不是透明！**（头发/眼睛/轮廓都是黑色）

**破解历程**：
1. 最初误认为8bpp灰度 → 用户确认灰度图轮廓正确但"还没有颜色"
2. 尝试H-TXT.PCX/RAIN.PCX的256色调色板 → 颜色偏蓝/偏紫
3. 分析像素值分布: 仅112个唯一值，其中15个是17的倍数（灰度特征），其余非连续
4. 发现规律: 值=高4位×16+低4位，高4位对应16色，低4位对应亮度
5. 用ED0.RGB调色板×亮度渲染 → 棕色头发、自然肤色、红色衣服，效果正确！
6. **修正透明色**: 最初误把值0当透明，导致黑色头发/眼睛消失。正确透明色是白色背景。

| 文件 | 实际尺寸 | 头部尺寸 | 条目数 | 调色板 | 内容 |
|------|----------|----------|--------|--------|------|
| FACE.MRG | 128x80/64x160 | 128x160 | 91 | ED0.RGB | 角色头像(彩色) |
| VS.MRG | 128x160 | 256x160 | 25 | 待确认 | 战斗画面/战车 |

#### B2: type=0x00 → 4bpp亮度遮罩 + 4玩家颜色着色（最终确认）
```
条目格式: 4字节解压大小(LE32) + LZSS压缩流 (NOWEAPON为未压缩)
解压后: 5字节头部(w=272 LE16, h=88, type=0x00, 保留2字节) + 11968字节4bpp数据
4bpp数据 = 连续的272x88线性像素, 每字节2像素(高4位=左像素, 低4位=右像素)
```

**核心发现：4bpp是16级亮度遮罩，不是颜色索引！272x88画面中横向排列4个单位，运行时分别用4种玩家颜色(RPGA)着色。**

- 画面布局: 272x88 = 4 × 68x88 单位横向排列
- 像素值含义: 0=透明, 1-15=从暗到亮的亮度级别
- 着色方式: 亮度级别 × 玩家颜色基色 = 最终RGB
  - 例如红色玩家: RGB = (255×t, 60×t, 60×t), t=亮度/15
- 4种玩家颜色: R(红)、P(紫)、G(绿)、A(黄/琥珀)，分别对应画面中从左到右的4个单位

**破解历程（三次误解→最终正确）**：
1. **误解1**: 8bpp 136x88 → 用户指出"一个里面有多张图，颜色不对"
2. **误解2**: 4bpp 272x88用PC-98标准16色调色板 → 颜色鲜艳不像军事色
3. **误解3**: 4帧68x88=R/G/B/A四通道组合RGB → 用户说"视觉上看起来都不对"
4. **误解4**: PDT位平面格式 → 噪点，确认是线性4bpp
5. **正确**: 单色16级亮度渲染后轮廓清晰 → 确认是亮度遮罩+玩家颜色着色

**关键验证**: 用任意单色的16级亮度渲染272x88整图，4个单位的轮廓都清晰可见。按x坐标分为4段，每段用不同玩家颜色着色，得到红/紫/绿/黄四个单位。

|------|----------|----------|--------|------|------|
| CANNON.MRG | 272x88 (4单位) | w=272,h=88 | 8 | LZSS | 炮兵单位(4玩家色) |
| PANZER.MRG | 272x88 (4单位) | w=272,h=88 | 8 | LZSS | 装甲单位(4玩家色) |

#### IDA确认的调色板硬件格式（sub_29D06，L41132）

游戏通过VGA端口 `0x3C8/0x3C9` 设置16色调色板，颜色存储为**2字节/色**：

```
字节0: 高4位 = R分量, 低4位 = B分量
字节1: 低4位 = G分量
转换: 4位值 × 135 >> 5 (近似 ×4) → VGA 6位值 → 再 ×4 → 8位
```

渲染4bpp单位图时，游戏为每个势力动态生成一套16色调色板：索引0=透明，索引1~15=势力基色的15级亮度渐变。4bpp数据直接作为调色板索引写入VRAM。

### 关键规律
- **头部尺寸 ≠ 实际像素尺寸**：头部的w/h是拉伸显示的目标尺寸，实际尺寸需通过数据量和多尺寸测试确定
- **type字段决定格式**：
  - 未压缩时 type=0x01 → 5帧1bpp动画
  - LZSS时 type=0x80 → 8bpp灰度（FACE/VS）
  - LZSS时 type=0x00 → 4bpp彩色+调色板（CANNON/PANZER/PLANE）
  - LZSS时 type=0x01 → 8bpp灰度（BSTAGE）
- **4bpp单位图**：CANNON/PANZER/PLANE为272x88亮度遮罩格式，4个单位横向排列，运行时用4种玩家颜色(RPGA)着色，索引0=透明，1-15=亮度级别

## 五、FACE.MRG 角色头像（LZSS+8bpp已确认）

### 条目格式
```
偏移  大小  说明
0     4     解压大小 (LE32) = 10245
4     ...   LZSS压缩数据
```

解压后:
```
偏移  大小  说明
0     2     显示h (LE16) = 128 (可能是目标显示尺寸)
2     2     显示w (LE16) = 160 (可能是目标显示尺寸)
4     1     type = 0x80 (8bpp标志)
5     10240 8bpp图像数据 (每字节1像素, 0-255灰度)
```

### 关键修正：8bpp不是4bpp
**之前错误地判断为4bpp 160x128**，导致彩色渲染出现水平条纹。

通过用户验证灰度图发现：
- `FACE_gray_w128.png` (128x80) 显示3个角色头像横向排列
- `FACE_gray_w64.png` (64x160) 显示1个完整竖版角色头像
- 数据范围0-255，确认是8bpp灰度

### 图像尺寸
- 10240字节8bpp = 10240像素
- 可能排列: 128x80（横版3表情）或 64x160（竖版立绘）
- 128x80更合理：每个条目包含2-3个角色表情头像
- 前4字节的128/160可能是拉伸显示的目标尺寸，非实际像素尺寸

### 已确认
- 108个条目，91个有效（跳过全白/全黑空条目）
- LZSS解压正确（大小10245字节）
- 8bpp灰度存储，数据范围0-255
- type=0x80表示8bpp格式

### 提取结果
- 91个128x80灰度头像: `extracted/HR_高报酬战将/face_128x80/`
- 91个64x160灰度头像: `extracted/HR_高报酬战将/face_64x160/`

### 经验教训
- **不要被头部的w/h值迷惑**：前4字节的128/160可能是显示尺寸，不是实际像素尺寸
- **灰度图多尺寸测试是关键**：把解压数据当作8bpp灰度，尝试不同宽度（64/80/128/160/320），能快速找到正确排列
- **4bpp条纹是格式误判的信号**：当4bpp渲染出现规律性条纹时，应考虑是否是8bpp或其他格式

- 位读取器（MSB优先）

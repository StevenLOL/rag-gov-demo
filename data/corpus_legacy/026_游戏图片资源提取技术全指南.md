## 1. 引言：为什么提取游戏资源是个难题

在现代游戏引擎（Unity、Unreal）中，资源通常以标准格式（PNG、OGG、FBX）存储在通用档案（.assets、.pak）中，提取工具成熟。但DOS/PC98时代的游戏完全不同：

- **无标准格式**：每个开发商、甚至每个游戏都有自定义格式
- **存储受限**：软盘容量有限（1.2MB~1.44MB），催生了各种精巧的压缩和位平面技术
- **硬件耦合**：图像格式与VGA/PC98硬件紧密绑定，位平面、调色板寄存器直接影响数据组织
- **文档缺失**：开发商不会公开格式规范，逆向是唯一途径

提取一个未知游戏的图片，本质上是回答五个问题：

1. **数据在哪？** — 归档结构、偏移表
2. **怎么解压？** — 压缩算法与参数
3. **颜色怎么来？** — 调色板位置与格式
4. **像素怎么排？** — 位平面布局、行宽、扫描顺序
5. **哪些是透明？** — 透明色索引与特殊像素处理

这五个问题构成了提取工作的完整链路，任何一个环节出错都会导致"有轮廓但颜色不对"或"颜色对但全是竖条纹"等典型失败模式。

## 2. 理论基础：DOS游戏图像的存储原理

### 2.1 VGA硬件与显示模式

DOS时代的图像格式深受VGA硬件架构影响。理解VGA的工作原理是破解格式的前提。

**VGA显示模式对比**：

| 模式 | 分辨率 | 色深 | 显存布局 | 典型用途 |
|------|--------|------|----------|----------|
| Mode 13h | 320×200 | 8bpp (256色) | 线性，1字节=1像素 | 绝大多数DOS游戏 |
| Mode X (未链化) | 320×240 | 8bpp | 4位平面，每地址对应4像素 | 高级编程、平滑滚动 |
| EGA 16色 | 320×200/640×350 | 4bpp (16色) | 4位平面 | 早期DOS游戏 |
| CGA | 320×200 | 2bpp (4色) | 打包像素，隔行存储 | 最早期游戏 |
| PC98 GRC | 640×400 | 4bpp (16色) | 4位平面，8像素块 | PC98游戏 |

**关键概念：位平面（Planar）vs 打包像素（Packed）**

这是DOS图像格式最核心的区分。以4bpp 16色图像为例：

**打包像素（Packed）**：每字节存2个像素，高4位=左像素，低4位=右像素
```
字节: [P0H|P0L] [P1H|P1L] [P2H|P2L] ...
```
优点：顺序读取简单；缺点：修改单个像素需要读-改-写

**位平面（Planar）**：4个独立的1bpp平面，像素索引=(p0<<3)|(p1<<2)|(p2<<1)|p3
```
平面0: [字节0] [字节1] ...  （每个字节的8位对应8个像素的第0位）
平面1: [字节0] [字节1] ...  （第1位）
平面2: [字节0] [字节1] ...  （第2位）
平面3: [字节0] [字节1] ...  （第3位）
```
优点：与VGA硬件天然匹配，写单个平面只需一次内存写；缺点：软件渲染需要跨平面读取

**位平面的三种常见布局**：

1. **平面连续（Contiguous）**：平面0全部数据 → 平面1 → 平面2 → 平面3
2. **按行交错（Row-interleaved）**：每行包含4个平面的数据，如FGP格式每行16字节=4平面×4字节
3. **8像素块（Block-8）**：每4字节控制8个像素的4个平面，PC98 GPC格式使用

![图1：打包像素 vs 位平面存储](images/026/fig1_planar_vs_packed.png)

> **实战经验**：位平面布局错误是"竖条纹"症状的最常见原因。我们在SANGUO三国英雄、ETIN倚天屠龙记等多个游戏中都遇到了这个问题。

### 2.2 调色板索引色（Indexed Color）

DOS游戏几乎全部使用索引色：像素值不是RGB，而是调色板的索引。

**常见调色板格式**：

| 类型 | 大小 | 位宽 | 值范围 | 特征 |
|------|------|------|--------|------|
| VGA 6位 | 48B(16色)/768B(256色) | 6位/通道 | 0-63 | 需×4转8位，最常见 |
| VGA 8位 | 768B(256色) | 8位/通道 | 0-255 | 直接使用 |
| PC98 4位 | 32B(16色) | 4位/通道 | 0-15 | 需<<4转8位，(G<<8)\|(R<<4)\|B |
| 内嵌4字节 | 64B(16色) | 8位/通道+属性 | 0-255 | 每色4字节，含属性字节 |
| HR复合 | 无独立调色板 | 高4位颜色+低4位亮度 | - | 8bpp像素本身含颜色和亮度 |

**调色板定位技巧**：
- 在文件中寻找连续的、值在0-63范围内的字节块
- 渲染为16×1或16×16的色带，观察是否有合理的颜色过渡（肤色、天空蓝、草地绿）
- 注意调色板可能在文件头部、尾部、或独立的.PAL/.RGB文件中

![图3：调色板索引色工作原理](images/026/fig3_indexed_color.png)

### 2.3 压缩算法家族

DOS游戏的压缩算法主要有三大类：

#### RLE（游程编码）

最简单也最常见的压缩。核心思想：用"计数+值"代替连续重复的字节。

**已验证的5种RLE变体**：

| 变体 | 规则 | 出现游戏 |
|------|------|----------|
| 跳过/复制型 | 0xFF=行结束, 0x80+=跳过, <0x80=复制N字节 | ETIN格式A（头像） |
| 偏移+像素型 | 每行[左偏移][像素...][0xFF] | ETIN格式B（地图瓦片） |
| 0跳过型 | 0=无操作, 1-127=重复, 128-255=字面量 | SUPER超时空英雄 |
| PCX高2位型 | 高2位=0xC0标记RLE,低6位=次数 | YFZ岳飞传、SANGUO |
| 双层RLE+异或+增量 | A控制8字节组, B控制组内字节, 异或解密, 增量解码 | PC98 GPC |

> **关键洞察**：RLE的"行结束"标记（通常0xFF）只在命令位置出现，字面量数据中的0xFF是像素值不是命令。这是ETIN格式A的核心规则。

![图4：RLE游程编码原理](images/026/fig4_rle.png)

#### LZSS（Lempel-Ziv-Storer-Szymanski）

基于滑动窗口的字典压缩。用"偏移+长度"引用之前出现过的数据。

**参数空间**：
- 窗口大小：4096 / 2048 / 1024（常见）
- 偏移位数：12 / 11 / 10
- 长度位数：4 / 5 / 6
- 位序：MSB优先 / LSB优先
- 最小匹配长度：2 / 3

> **实战经验**：LZSS参数组合有数百种，盲目测试效率低。我们的`lzss_decoder.py`实现了自动参数搜索，通过解压结果的合理性（非零字节比例、多样性）评分。

#### LZW（Lempel-Ziv-Welch）

基于字典的压缩，GIF格式使用。JPM金瓶梅的MGP2格式使用了一个**非标准变体**。

**标准LZW vs MGP2变体**：
- 标准：清除码（clear_code）后的第一个代码不增加next_code
- MGP2变体：清除后的第一个代码**也增加**next_code，即使不添加字典条目

这个微小差异导致标准LZW解码器对ITEM.PAT等文件完全失败，而变体解码器能正确输出。

### 2.4 归档与容器格式

游戏资源通常打包在归档文件中。常见结构：

```
┌─────────────────┐
│  魔数/签名       │  ← 格式识别的第一步
├─────────────────┤
│  头部元数据      │  ← 版本、条目数、标志位
├─────────────────┤
│  偏移表          │  ← 每个条目的偏移和大小
│  (通常u32数组)   │
├─────────────────┤
│  条目1数据       │
│  条目2数据       │
│  ...            │
└─────────────────┘
```

**已验证的归档格式**：

| 格式 | 魔数 | 条目结构 | 游戏 |
|------|------|----------|------|
| MRG | 无（u16 count开头） | u32绝对偏移数组 | HR高报酬战将 |
| GRP/IDX | 无（配对文件） | IDX=u32偏移数组, GRP=数据 | ETIN倚天屠龙记 |
| GRP | "GRP"(3字节) | 19字节条目(offset+size+w2+w+h) | SANGUO三国英雄 |
| PIC | "LIB\x01" | 19字节条目(含f1-f5尺寸字段) | YFZ岳飞传 |
| MGP2 | "MGP2" | 8字节条目(宽高+3字节偏移) | JPM金瓶梅 |
| IND/CEL | 无（配对文件） | IND=108字节记录(13条带×8字节) | SUPER超时空英雄 |

## 3. 核心问题：提取过程中的五大挑战

### 3.1 格式识别：扩展名是谎言

**核心矛盾**：文件扩展名不代表格式。

- XIAKE侠客的`.GPC`文件头部是`26 80 a0 00`，与PC98 GPC的`PC98)GPCFILE`完全不同
- 同一扩展名在不同游戏中可能是完全不同的格式

**正确做法**：永远检查文件头部的魔数（Magic Number），不看扩展名。

**常见魔数速查**：
```
PC98)GPCFILE  → PC98 GPC图像
PC98)FGP      → PC98 FGP角色精灵
MGP2          → 金瓶梅图像包
GRP           → 三国英雄瓦片包（注意只有3字节，第4字节是count低字节）
MAP2          → 三国英雄地图（宽高是大端！）
LIB\x01       → 岳飞传PIC归档
LIB\x00       → 岳飞传MAN.LIB角色库
PKLITE        → PKLITE压缩的EXE，需先解压
```

### 3.2 压缩解码：参数空间爆炸

**核心矛盾**：LZSS有数百种参数组合，RLE有多种变体，LZW还有非标准变体。

**方法论**：
1. 先判断压缩类型（字节分布特征）
   - 0x00占比极低、无连续相同字节 → LZW
   - 有大量0x00但结构规律 → RLE
   - 混合原始字节和引用模式 → LZSS
2. 对LZSS使用自动参数搜索（我们的`find_lzss_params()`）
3. 对RLE逐一测试5种已验证变体
4. 对LZW先试标准，失败后试MGP2变体

### 3.3 调色板还原：位置与位宽

**核心矛盾**：调色板可能在任何位置，位宽可能是4/6/8位，顺序可能是RGB/GRB/BGR。

**典型错误**：
- PC98 4位调色板忘记左移4位 → 颜色偏暗
- VGA 6位调色板忘记×4 → 颜色偏暗
- 调色板顺序搞反（G/R/B vs R/G/B）→ 颜色整体偏色

**验证方法**：渲染调色板为色带，检查是否有合理的肤色（R>G>B）、天空蓝（B>R）、草地绿（G>R）。

### 3.4 图像布局：竖条纹的根源

**核心矛盾**：位平面布局错误是最常见的失败模式，症状是"有轮廓但全是竖条纹"。

**三大布局陷阱**：

1. **平面顺序错误**：p0/p1/p2/p3的组合顺序不对
2. **位序错误**：MSB优先 vs LSB优先
3. **行宽陷阱**：RLE解码行宽w2 ≠ 实际图像宽度w（SANGUO的w2=80, w=72，多出的8字节是行尾元数据）

**单色平面验证法（最重要的方法论）**：
当4bpp组合有条纹时，不要继续猜组合方式。先单独渲染每个位平面的1bpp单色图像：
- 如果某个平面有清晰轮廓 → 数据布局方向正确，只需修正平面组合
- 如果所有平面都是噪点 → 布局方向错误，需要换布局（连续/行交错/8像素块）

我们的`planar_renderer.py`支持3种布局×2种位序×24种平面顺序=144种组合的穷尽测试。

### 3.5 透明处理：0不一定是透明

**核心矛盾**：透明色索引不总是0。

- 大多数游戏：索引0=透明（黑色背景）
- HR高报酬战将FACE头像：**透明色是白色(255,255,255)**，索引0是黑色（头发、眼睛、轮廓）
- PC98 GPC：transcolor字段明确指定透明色索引（通常=2）

**错误后果**：把HR的0当透明会导致人物的黑色头发、眼睛、轮廓全部消失，只剩下彩色部分。

## 4. 五步法：从二进制到可视图像

基于12个游戏的逆向实践，我们总结出一套可复现的五步法。

![图2：游戏图片提取五步法](images/026/fig2_five_steps.png)

### 步骤1：文件结构探查

**目标**：了解文件的基本结构和可能的格式。

**操作**：
```python
from probe import probe_file
probe_file('unknown.dat')
```

**检查项**：
- 文件大小、头部16字节、魔数
- 字节值分布（最常见字节、唯一值数量）
- 是否有连续的0-63范围字节（可能的调色板）
- 目录中是否有配对文件（.IDX+.GRP, .IND+.CEL, .GS+.RGB）

**产出**：格式假设清单（可能是GPC？可能是LZSS压缩？可能有内嵌调色板？）

### 步骤2：调色板定位与验证

**目标**：找到调色板并确认颜色正确。

**操作**：
1. 检查文件头部/尾部是否有调色板特征
2. 检查同目录是否有.PAL/.RGB/.COL文件
3. 将候选调色板渲染为色带验证
4. 注意位宽转换（6位→×4，4位→<<4）

**产出**：确认的16色或256色调色板（RGB数组）

### 步骤3：压缩识别与解码

**目标**：识别压缩算法并正确解压。

**操作**：
1. 根据字节分布判断压缩类型（RLE/LZSS/LZW/无压缩）
2. 对RLE：测试5种变体（`rle_decoders.py`）
3. 对LZSS：自动参数搜索（`lzss_decoder.py`的`find_lzss_params()`）
4. 对LZW：先标准后MGP2变体（`lzw_decoders.py`）
5. 验证解压结果：大小是否合理（w×h×bpp/8），是否有结构规律

**产出**：解压后的原始像素数据（或位平面数据）

### 步骤4：图像布局验证

**目标**：确定像素数据的正确布局并渲染。

**操作**：
1. 先尝试最简单的4bpp打包渲染
2. 如果有条纹，使用**单色平面验证法**：
   ```python
   from planar_renderer import render_planes
   planes = render_planes(data, width, height, layout='row_interleaved')
   # 检查每个平面是否有轮廓
   ```
3. 根据平面验证结果，确定正确的布局和平面组合
4. 注意行宽陷阱：RLE解码行宽可能≠实际渲染宽度
5. 注意翻转：部分格式需要上下翻转（JPM MGP2）或不翻转（PC98 GPC）

**产出**：正确渲染的索引色图像

### 步骤5：反汇编印证（可选但推荐）

**目标**：通过反汇编主程序确认格式细节，解决纯数据分析无法确定的问题。

**操作**：
1. 用IDA Pro加载游戏EXE（16位DOS程序选8086处理器）
2. 搜索错误消息字符串（如"MGP2$:Patterns are not in correct Format!"）
3. 定位字符串引用的函数 → 资源加载逻辑
4. 分析文件读取、解压、VGA端口操作的调用链
5. 关注VGA序列控制器（0x3C4）和图形控制器（0x3CE）的操作

**产出**：格式的权威确认，以及之前猜测错误的修正

> **注意**：反汇编能确认机制，但具体数据组织仍需图像验证。两者是互补关系，不是替代关系。

## 5. 实战案例：四个典型格式的破解历程

### 案例1：PC98 GPC格式 — 双层RLE+异或+增量解码的层层嵌套

**游戏**：YOHGAS妖精战士（ロマンスは剣の輝き）、K2华丽的人生2

**背景**：GPC是PC98平台上IDLES公司常用的图像格式，CSDN博客有公开的C代码参考。

**破解过程中的两个关键bug**：

**Bug 1：p_target连续性导致竖条纹**

博客代码中，RLE解码的`p_target`在循环外初始化为`decode_buf`，每行解码后保持位置，下一行从上次的位置继续（因为post_decode_3会移动剩余数据到开头）。

我们最初实现时，每行RLE解码都从`p=0`开始，导致每行数据错位，产生竖条纹。

修复：`p_target`必须在循环外初始化，保持跨行连续性。

**Bug 2：垂直翻转方向错误**

博客代码使用`dest = (height-i-1)*bpl`（垂直翻转），但YOHGAS的G001.GPC森林场景中角色倒挂、LOGO文字镜像。

测试4种翻转组合后确认：YOHGAS的GPC不需要垂直翻转，用`dest = i*bpl`。

**最终算法（5步后处理）**：
1. 双层RLE解码（A控制8个8字节组，B控制组内8字节）
2. 异或解密（decode_buf[0]为步长，对后续字节做链式异或）
3. 增量解码（与disp_buf异或，实现帧间差异压缩）
4. 移动剩余数据到开头（为下一行做准备）
5. 4平面转4bpp（8像素块布局，MSB优先）

**验证结果**：292张GPC全部正确提取，包括@YOGICON图标工具栏、LOGO标题、G001森林场景等。

**经验教训**：
- 参考实现的细节（如p_target初始化位置）不能忽略
- 参考实现的假设（如垂直翻转）不一定适用于所有变体，必须用真实图像验证

### 案例2：SANGUO三国英雄GRP — 行宽陷阱导致的竖条纹

**游戏**：三国英雄传（智冠科技）

**背景**：GRP是地图瓦片包，每个瓦片用PCX风格RLE压缩。

**问题现象**：提取的瓦片右侧有规律的竖条纹，轮廓正确但颜色不对。

**根因分析**：
GRP条目结构中有两个宽度字段：
- `w2`（偏移8）：RLE解码的行宽 = 80
- `w`（偏移10）：实际图像宽度 = 72

我们最初用w2=80作为渲染宽度，导致x=72~79的行尾元数据被当作像素显示，形成右侧竖条纹。

tile0的x73-79固定为`[117,5,243,165,235,104,144]`（所有行相同），tile3的x73-79固定为`[0,162,128,0,0,0,0]`——这些明显不是图像像素。

**修复**：RLE用w2=80解码，但渲染时只取前w=72列。

**另一个坑：GRP魔数只有3字节**

文件头是`47 52 50 45 00`，最初误认为魔数是"GRPE"（4字节）。实际上"GRP"只有3字节，第4字节`0x45`是count的低字节（count=0x0045=69）。

**验证结果**：23关共1841个瓦片正确提取，包括等距菱形地面瓦片、树木、建筑等。

**经验教训**：
- 归档条目中的多个"宽度"字段含义不同，需区分解码行宽和渲染宽度
- 魔数长度要精确验证，不能想当然认为是4字节

### 案例3：HR高报酬战将 — 8bpp复合格式与4bpp亮度遮罩

**游戏**：高报酬战将（HIGH REWARD，IMAGINEER/ENIX）

**背景**：PC98移植的DOS战略游戏，MRG归档包含多种图像类型。

**两个反直觉的发现**：

**发现1：8bpp不是256色调色板，而是"高4位颜色+低4位亮度"**

FACE.MRG的角色头像解压后是8bpp数据。最初尝试：
- 当作灰度 → 轮廓正确但"还没有颜色"
- 用H-TXT.PCX的256色调色板 → 颜色偏蓝/偏紫

分析像素值分布：仅112个唯一值，其中15个是17的倍数（灰度特征），其余非连续。

**突破**：值=高4位×16+低4位。高4位对应16色调色板索引（ED0.RGB），低4位对应亮度级别（0-15）。

着色公式：`RGB = (base_r × bright/15, base_g × bright/15, base_b × bright/15)`

效果：棕色头发、自然肤色、红色衣服，完全正确！

**发现2：4bpp不是颜色索引，而是16级亮度遮罩**

CANNON.MRG炮兵单位解压后是4bpp数据，尺寸272×88。

最初尝试：
- 用PC98标准16色调色板 → 颜色鲜艳不像军事色
- 当作4帧68×88的R/G/B/A通道 → 视觉上完全不对

**突破**：272×88画面横向排列4个单位，4bpp是16级亮度遮罩。运行时分别用4种玩家颜色（R红/P紫/G绿/A黄）着色：
`RGB = player_color × brightness/15`

用任意单色的16级亮度渲染整图，4个单位的轮廓都清晰可见。按x坐标分为4段，每段用不同玩家颜色着色，得到红/紫/绿/黄四个单位。

**透明色修正**：
最初误把值0当透明，导致人物黑色头发/眼睛消失。正确透明色是**白色(255,255,255)**，对应值255（索引15+亮度15）。

**经验教训**：
- 8bpp不一定是256色调色板，可能是"颜色+亮度"复合格式
- 4bpp不一定是颜色索引，可能是亮度遮罩（运行时着色）
- 透明色不一定是0，需根据实际图像判断

### 案例4：JPM金瓶梅MGP2 — LZW变体的一个字节差异

**游戏**：金瓶梅（Golden Jug）

**背景**：MGP2（MG Patterns Vol 1.1）格式，*.PAT文件包含图像资源。

**问题**：标准GIF风格LZW对TITLE.PAT有效，但对ITEM.PAT等文件失败。

**分析**：
- TITLE条目0前4字节：`00 3F 08 1C` → 清除→字面量31→字典码258，有效
- ITEM条目0前4字节：`00 01 02 18` → 清除→清除→字面量0→代码259，**标准LZW判定无效**

标准LZW中，清除后的第一个代码（prev=None）不添加字典条目，next_code保持258。代码259不在字典中且≠next(258)，报错。

**突破：LZW变体**

这个游戏的LZW实现不同——**清除后的第一个代码也增加next_code**（即使不添加字典条目）。

```
标准LZW:  清除→prev=None→字面量0→输出[0], next保持258→代码259→无效！
MGP2变体: 清除→prev=None→字面量0→输出[0], next+=1→259→代码259==next→KwK!输出[0,0]
```

KwK（Konami vs Kawasaki）规则：当code==next_code且prev非空时，entry=prev+prev[0]。

**验证**：直接用ITEM原始数据LZW解压→6399字节（80×80=6400，差1字节末像素补0），所有45个80×80物品图标全部正确：花朵、宝箱、餐具、梯子、船等形状完整。

**后处理**：解压后图像上下颠倒，需FLIP_TOP_BOTTOM。

**经验教训**：
- LZW等标准算法可能有非标准变体，差异可能只在一个边界条件
- 不要用一个文件的头部替换另一个文件的头部（会污染字典）
- 清除码后的边界行为是LZW变体的常见差异点

## 7. 常见错误排查表

| 症状 | 可能原因 | 排查方向 |
|------|----------|----------|
| 全是噪点/雪花 | 压缩算法错误或参数错误 | 检查压缩类型，LZSS用自动参数搜索 |
| 有轮廓但全是竖条纹 | 位平面布局错误或行宽≠渲染宽度 | 单色平面验证法；检查w2 vs w |
| 轮廓对但颜色偏暗 | 调色板位宽未转换 | 6位→×4，4位→<<4 |
| 颜色整体偏色 | 调色板顺序错误（RGB/GRB/BGR） | 交换通道顺序测试 |
| 图像上下颠倒 | 翻转方向错误 | 测试4种翻转组合（不翻/上下/左右/都翻） |
| 只有上半部分 | 隔行扫描未处理 | 检查scans字段，外层循环scans次 |
| 人物黑色部分消失 | 透明色判断错误 | HR等游戏透明色是白色不是0 |
| 每行数据错位 | RLE跨行状态未保持 | GPC的p_target需循环外初始化 |
| 部分文件正确部分失败 | 同归档内有多种子格式 | 检查条目type字段，分类处理 |
| 物品图标形状倾斜/撕裂 | LZW变体不匹配 | 试MGP2变体（清除后第一个代码也增加next） |
| 右侧有规律竖条纹 | RLE行宽>实际宽度 | 检查w2字段，渲染只取前w列 |
| 颜色鲜艳但不像游戏风格 | 4bpp被误当颜色索引 | 可能是亮度遮罩，用单色渲染验证 |

## 8. 法律与伦理考量

游戏资源提取涉及法律和伦理问题，需注意：

1. **版权保护**：游戏图像、音频等资源受版权保护，提取的资源仅供个人学习研究使用，不得用于商业目的或重新分发
2. **逆向工程合法性**：在多数司法辖区，为互操作性、安全研究、个人学习目的的逆向工程是合法的，但具体法律因地区而异
3. **修改与分发**：修改游戏资源或制作MOD可能违反游戏的最终用户许可协议（EULA）
4. **开源工具使用**：QuickBMS、Ghidra等工具有各自的开源协议，使用时需遵守
5. **本文目的**：本文所述技术用于软件保护研究、游戏历史保存、教育目的，不鼓励任何侵权行为

## 9. 结语

游戏资源提取是一门结合了硬件知识、压缩算法、逆向工程和图像渲染的综合技术。从VGA位平面到LZW变体，从调色板位宽到行宽陷阱，每个细节都可能决定提取的成败。

本文提出的五步法（探查→调色板→压缩→布局→反汇编）和单色平面验证法，经过12个真实游戏的验证，能够系统性地解决大多数DOS/PC98游戏的图像提取问题。核心思想是：**不要盲目猜测，用数据特征引导方向，用真实图像验证结果**。

随着AI辅助逆向工具的发展（如Ghidra+LLM），格式破解的效率会不断提高。但对底层原理的理解——位平面如何工作、压缩算法如何变体、调色板如何编码——仍然是不可替代的基础。
